# 엔진·에디터·클라이언트 개발 목표와 작성 지침

## 1. 문서의 목적

이 문서는 BamEngine의 장기 목표와 설계 판단 기준을 정의한다.
여기에 적힌 기능이 현재 구현되었거나 검증되었다는 뜻은 아니다.

작업 방식과 코드 평가 기준은 루트 AGENTS.md를 따른다.
리플렉션과 직렬화의 세부 원칙은 Docs/ReflectionArchiveGuidelines.md를 따른다.

현재 구현 상태와 단기 작업 순서는 개발 계획 및 구현 기록에서 관리한다.
장기 목표에 포함되었다는 이유만으로 모든 기능을 한 번에 구현하지 않는다.

## 2. 최종 목표

BamEngine은 다음 결과물을 제작하고 실행할 수 있는 엔진과 에디터를 목표로 한다.

- 2D 및 3D 게임
- V-Tuber용 아바타 구동 애플리케이션
- 애니메이션과 리깅 관련 실험 및 최적화 도구
- 강화학습과 연결되는 시뮬레이션 환경
- 사용자 코드와 외부 플러그인으로 기능을 확장한 애플리케이션

에디터는 콘텐츠 제작, 실행 검증, 디버깅, 빌드 및 패키징을 지원한다.
사용자는 필요한 기능을 선택하고 조합하여 프로젝트를 구성할 수 있어야 한다.

범용성은 실제로 서로 다른 프로젝트가 공통 기반을 재사용하는 것으로 확인한다.
특정 프로젝트의 모든 기능을 엔진 핵심에 포함하는 것을 범용성의 기준으로 삼지 않는다.

## 3. Engine, Editor, Client의 책임

### Engine

프로젝트를 실행하는 데 필요한 공통 기능과 확장 지점을 제공한다.

- 객체와 컴포넌트의 생명주기
- 씬과 실행 상태 관리
- 시간 진행과 시스템 실행
- 리소스 조회와 실행용 데이터 로딩
- 렌더링, 입력, 물리, 애니메이션 등 실행 기능
- 리플렉션과 직렬화의 엔진 연결
- 스크립트와 그래프의 실행
- 런타임 확장 기능의 등록과 사용

Engine은 Editor의 창, 패널, 선택 상태, 편집 명령에 의존하지 않는다.
개별 게임이나 아바타 프로젝트의 규칙을 공통 실행 코드에 넣지 않는다.

### Editor

사용자가 프로젝트와 콘텐츠를 제작하고 검증하는 환경을 제공한다.

- 프로젝트 생성과 설정
- 에셋 임포트와 관리
- 씬, 컴포넌트, 리소스 속성 편집
- 선택, 기즈모, Undo/Redo
- 스크립트 및 Visual Scripting 제작 지원
- PIE, 일시정지, 단계 실행과 디버깅
- 변경 감지와 핫 리로드 제어
- 빌드 및 패키징 작업의 설정과 실행

콘텐츠의 실제 실행에는 Engine의 기능을 사용한다.
Editor에만 존재하는 별도의 게임 실행 규칙을 만들지 않는다.

### Client

Editor 없이 프로젝트를 실행하는 독립 애플리케이션이다.
이 문서에서 Client는 네트워크 접속 기능의 존재를 의미하지 않는다.

- 실행 설정과 프로젝트 로딩
- 필요한 플랫폼 기능과 Engine 초기화
- 프로젝트 코드와 런타임 플러그인 연결
- 실행 루프와 종료 처리
- 오류 보고와 실행 로그

Client는 Editor의 실행 파일, 패널, 편집 상태에 의존하지 않는다.
배포된 실행에 불필요한 제작 도구를 필수 의존성으로 포함하지 않는다.

### 프로젝트 코드와 제작 도구

게임 규칙, 아바타 동작 등 프로젝트 고유의 코드는
Editor의 PIE와 Client에서 함께 사용할 수 있는 위치에 둔다.

이를 위해 필요한 경우 프로젝트 모듈이나 플러그인으로 분리한다.
처음부터 별도의 실행 파일이나 복잡한 모듈 체계를 강제하지 않는다.

임포트, 데이터 변환, 코드 생성, 빌드 및 패키징 처리는
Editor UI 없이도 호출할 수 있는 도구 또는 공통 처리 코드로 구성한다.

## 4. 의존성과 실행 상태

기본 의존 방향은 다음과 같다.

- Editor는 Engine과 제작 도구를 사용한다.
- Client는 Engine과 프로젝트 실행 코드를 사용한다.
- 프로젝트 실행 코드와 런타임 플러그인은 공개된 실행 API를 사용한다.
- Editor 전용 확장은 Editor의 확장 API를 사용할 수 있다.
- 독립적인 기반 모듈은 Engine이나 Editor에 역으로 의존하지 않는다.

공개 인터페이스에는 소비자가 실제로 필요한 정보만 노출한다.
외부 라이브러리 자료형을 공개할 때는 그에 따른 결합과 교체 비용을 고려한다.

씬, 물리, 스크립트, 그래프, 타이머 등 변경 가능한 실행 상태의 소유자를 명확히 한다.
공유 가능한 리소스와 실행마다 달라지는 상태를 구분한다.

새로운 전역 상태를 추가하기 전에 다음 사용 흐름에 미치는 영향을 확인한다.

- PIE의 반복 시작과 종료
- 씬 교체와 재시작
- 서로 독립적인 시뮬레이션 실행
- 테스트 간 상태 초기화

기존 싱글턴을 일괄 제거하는 것을 목표로 삼지 않는다.
실행 상태가 섞이는 문제가 확인되는 범위부터 책임과 수명을 조정한다.

## 5. 시간 진행과 시뮬레이션

시뮬레이션의 진행과 화면 렌더링의 실행을 구분한다.

- 고정 스텝의 크기와 실행 횟수를 명확히 관리한다.
- Editor, Client, 학습 환경에서 같은 시뮬레이션 규칙을 사용한다.
- 일시정지와 한 스텝 실행의 의미를 정의한다.
- 실시간 실행의 지연 처리와 학습용 스텝 진행 정책을 구분한다.
- 렌더링이 필요 없는 작업은 창과 렌더러 없이 진행할 수 있도록 한다.

영상 관측이 필요한 학습은 화면 밖 렌더링과 GPU를 사용할 수 있다.
헤드리스 실행을 GPU 사용 금지와 같은 의미로 취급하지 않는다.

2D와 3D 기능은 필요한 공통 기반을 공유한다.
물리나 좌표 처리처럼 의미가 다른 부분까지 같은 구현으로 강제하지 않는다.

## 6. 데이터와 리플렉션

리플렉션 정보는 속성 편집, 직렬화, 스크립트 및 그래프 연결에 활용한다.
같은 정보를 기능마다 반복 등록하는 부담을 줄인다.

다만 다음 정책은 구분한다.

- 리플렉션에서 조회할 수 있는 대상
- 저장하고 복원할 대상
- 사용자가 편집할 수 있는 대상
- 스크립트나 그래프에서 호출할 수 있는 대상

리플렉션 등록만으로 모든 멤버와 함수를 모든 기능에 노출하지 않는다.

저장 데이터의 타입, 필드, 객체와 리소스 참조는
다시 실행하거나 파일을 이동해도 해석할 수 있는 식별 정책을 사용한다.
메모리 주소를 영속적인 식별자로 사용하지 않는다.

데이터 형식 변경에는 버전, 기본값, 변환 및 지원 중단 정책을 정의한다.
복원할 수 없는 데이터를 조용히 생략하거나 성공으로 처리하지 않는다.

## 7. 사용자 확장과 플러그인

사용자가 엔진 핵심 소스를 반복 수정하지 않고
새로운 기능을 등록할 수 있는 확장 지점을 제공한다.

필요한 확장 대상은 다음과 같다.

- 컴포넌트와 시스템
- 리소스 형식과 임포터
- Inspector 편집기와 Editor 패널
- 스크립트 바인딩과 그래프 노드
- 프로젝트별 실행 기능

플러그인은 런타임, Editor, 제작 도구 중 필요한 부분을 구분한다.
배포에는 실행에 필요한 부분만 포함할 수 있어야 한다.

플러그인에는 의존성, 초기화 순서, 종료 책임과 호환 범위를 정의한다.
네이티브 플러그인은 지원하는 컴파일러와 빌드 조건도 명시한다.

기능 확장과 실행 중 DLL 교체는 별도의 요구로 취급한다.
초기에는 재빌드와 재시작이 필요한 확장 방식도 허용한다.

동적 언로드를 지원할 때는 해당 모듈의 객체, 작업, 콜백,
함수 참조와 타입 등록이 남아 있는 상태에서 코드를 제거하지 않는다.

## 8. Visual Scripting

Visual Scripting은 노드와 연결을 통해 실행 동작을 작성하는 기능이다.

그래프 편집 UI와 그래프 데이터 및 실행 처리를 분리한다.
Client는 Editor UI 없이 저장된 그래프를 실행할 수 있어야 한다.

다음 실행 규칙을 명확히 정의한다.

- 핀의 자료형과 연결 가능 조건
- 실행 흐름과 데이터 평가 순서
- 이벤트, 변수와 그래프 인스턴스의 상태
- 반복, 재진입과 실행량 제한
- 컴파일 오류와 실행 오류의 전달

오류는 가능한 한 해당 그래프, 노드와 핀을 식별하여 보고한다.
사용자 코드와 플러그인에서 노드를 추가할 수 있도록 한다.

게임 로직, 셰이더, 애니메이션 그래프를
처음부터 하나의 실행 체계로 통합하는 것을 전제로 삼지 않는다.
공통화는 실제로 공유되는 요구가 확인된 범위에서 진행한다.

## 9. 핫 리로드

핫 리로드는 종류마다 지원 범위와 상태 유지 정책을 따로 정의한다.

### 셰이더

- 새 코드의 컴파일과 파이프라인 생성을 확인한 뒤 교체한다.
- 실패하면 기존의 사용 가능한 셰이더를 유지한다.
- 바인딩 구조 변경은 관련 머티리얼과 리소스의 호환성을 확인한다.
- GPU가 사용 중인 자원을 너무 일찍 해제하지 않는다.

### 스크립트와 그래프

- 새 코드 또는 그래프의 검증 후 교체한다.
- 실행 중인 호출과 인스턴스 상태의 처리 정책을 정의한다.
- 유지할 상태, 초기화할 상태와 변환할 상태를 구분한다.
- 오류를 수정하고 다시 적용할 수 있는 흐름을 제공한다.

### 리플렉션과 네이티브 코드

- 메타데이터 갱신, 함수 구현 변경, 객체 구조 변경을 구분한다.
- 타입 정보 교체 시 이를 참조하는 캐시와 바인딩을 갱신한다.
- 객체 구조 변경에는 기존 인스턴스와 참조의 재구성 여부를 판단한다.
- 안전하게 적용할 수 없는 변경은 재시작이 필요하다고 명확히 알린다.

파일 변경 감지만 구현된 상태를 핫 리로드 완료로 취급하지 않는다.
감지, 검증, 교체, 상태 처리와 실패 복구까지 확인한다.

## 10. PIE와 편집 상태 보호

PIE는 Editor에서 현재 프로젝트의 실행 동작을 확인하는 기능이다.

- 실행 중 발생한 변경이 원본 편집 데이터를 의도치 않게 덮어쓰지 않는다.
- 시작 실패와 종료 실패에서도 편집 데이터의 보존을 우선한다.
- 종료 시 실행용 객체, 작업, 이벤트, 타이머와 외부 연결을 정리한다.
- 일시정지 중에도 필요한 Editor 조작과 화면 갱신은 가능해야 한다.
- 편집용 미리보기와 실제 시뮬레이션의 업데이트 범위를 구분한다.

초기 단일 PIE에서는 저장과 복원 방식도 사용할 수 있다.
이 경우 저장 대상 밖의 실행 상태까지 초기화되는지 검증한다.

편집 상태와 실행 상태를 별도 인스턴스로 관리할 필요가 생기면
공유할 데이터와 분리할 상태를 명확히 한다.

PIE에서 유지할 변경을 편집 상태로 반영하는 기능은 별도 작업으로 취급한다.
Undo/Redo와 선택 상태가 무효화되는 조건도 함께 정의한다.

## 11. 아바타와 강화학습 활용

### 아바타와 애니메이션

아바타 구동에 필요한 애니메이션, 스키닝, 표정과 제약 처리는
실제 지원 대상에 맞추어 단계적으로 구현한다.

외부 추적 장치나 프로그램에서 들어오는 데이터는
공통 동작 데이터로 변환하여 실행 기능에 전달한다.

특정 장치의 통신 방식이나 특정 아바타 형식의 세부 처리는
관련 모듈 또는 플러그인에서 담당한다.

### 강화학습과 최적화

시뮬레이션 환경은 다음 항목을 명시적으로 제공한다.

- 초기 상태 설정과 환경 초기화
- 행동 입력과 시뮬레이션 진행
- 관측 데이터와 보상
- 과제의 종료와 시간 제한에 의한 중단
- 난수 시드와 재현 조건
- 실행 결과와 평가 지표 기록

학습 알고리즘과 프레임워크는 필요에 따라 외부 도구로 연결한다.
학습 결과를 사용하는 데 필요한 추론 기능과 학습 도구의 의존성을 구분한다.

애니메이션 또는 리깅 최적화에서는 먼저 다음을 정의한다.

- 변경할 대상과 허용 범위
- 품질, 오차, 비용 등 평가 지표
- 반드시 유지해야 할 제약
- 결과물을 저장하고 실제 실행에 적용하는 방법

강화학습을 사용한다는 사실만으로 최적화가 달성되었다고 판단하지 않는다.
동일한 평가 조건에서 기존 방식과 결과를 비교한다.

고정 스텝과 난수 시드만으로 모든 환경의 완전한 결정성을 보장한다고 주장하지 않는다.
재현 가능한 플랫폼, 의존성 버전과 오차 범위를 검증 결과로 기록한다.

## 12. 빌드와 패키징

Editor는 프로젝트의 대상 플랫폼과 빌드 구성을 선택하고
빌드 및 패키징 작업을 실행할 수 있어야 한다.

처리 과정은 다음 책임을 구분한다.

- Build: 엔진, 프로젝트 코드와 필요한 플러그인 빌드
- Cook: 원본 에셋을 대상 플랫폼의 실행용 데이터로 변환
- Stage: 실행 파일, 라이브러리, 데이터와 설정을 배포 폴더에 수집
- Package: 배포 형식으로 구성

초기에는 배포 폴더 형태로도 완료 기준을 충족할 수 있다.
압축 파일이나 설치 프로그램은 필요에 따라 추가한다.

동일한 설정으로 Editor UI 없이도 해당 작업을 실행할 수 있도록 한다.
누락된 리소스와 플러그인 의존성을 확인하고 실패 원인을 보고한다.

패키징된 Client는 개발자의 소스 경로와 Editor 설치에 의존하지 않아야 한다.
실행 중 이름이나 설정으로 선택하는 에셋은 명시적으로 패키징에 포함할 수 있어야 한다.

## 13. 구현 순서와 완료 기준

기존 구현을 활용하여 작은 사용 흐름부터 완성한다.

권장하는 초기 흐름은 다음과 같다.

1. 작은 씬을 편집하고 저장한다.
2. 다시 불러와 데이터와 참조를 확인한다.
3. PIE로 실행하고 종료하여 편집 상태를 확인한다.
4. 같은 프로젝트를 Client에서 실행한다.
5. 배포 폴더를 만들어 개발 경로 밖에서 실행한다.

이 흐름을 기반으로 사용자 확장, 핫 리로드, Visual Scripting,
아바타와 학습 환경을 각각 검증 가능한 단계로 추가한다.

각 기능에는 다음 내용을 기록한다.

- 사용자가 수행할 작업
- 사용자가 작성하거나 등록해야 할 코드와 데이터
- 시스템이 자동 처리하는 범위
- 정상 결과와 실패 시 동작
- 지원 범위와 현재 제한
- 완료 판단에 사용한 검증 결과

확장성은 외부 예제로 새 기능을 추가하는 과정으로 확인한다.
편의성은 사용자에게 요구되는 반복 작업과 오류 수정 과정으로 평가한다.
성능은 동일한 조건의 측정 결과로 판단한다.

## 14. 로캘과 입력 처리의 공통 기준

신규 기능과 기존 기능 수정에서는 로캘 키와 InputManager 사용을 기본 구현 기준으로 삼는다.
개발 계획에도 필요한 키·입력 API와 검증 항목을 포함하여 기능 구현 뒤의 별도 정리 작업으로 미루지 않는다.
기존 위반은 현재 변경 범위와 연결되는 부분부터 개선하고, 무관한 코드까지 일괄 재작성하지 않는다.

### 로캘 키와 표시 문구

- 사용자가 읽는 고정 문구는 LocalizationManager의 키로 조회한다.
  창 제목·버튼·메뉴·콤보 항목·툴팁·알림·오류 안내와 리플렉션 표시 이름·분류·설명을 포함한다.
  배열·조건식·변수를 거쳐 UI에 전달되는 문구도 같은 기준을 적용한다.
- 먼저 기존 키를 찾아 재사용한다. 새 키는 의미와 기능을 식별할 수 있는 안정적인 이름으로 만들고,
  `Resources/Data/Localization/Engine.csv` 또는 `Editor.csv`에 영어·한국어 번역을 함께 등록한다.
  JSON은 기존 변환·빌드 경로로 생성하며, 생성 파일만 수정하여 원본 CSV와 다르게 만들지 않는다.
- Editor의 표시에는 기존 LOCAL·LOCAL_LABEL·LOCAL_FMT 경로를 활용한다.
  번역된 표시 이름과 내부 ID를 구분하여 언어 변경으로 선택·편집 상태가 초기화되지 않게 한다.
  문장 조각을 이어 붙이기보다 번역 서식과 인자를 사용하고 언어 간 서식 인자의 일치를 확인한다.
- Engine은 Editor 전용 매크로에 의존하지 않는다. 독립 모듈의 오류를 표시하려면
  오류 코드·키·상세 정보를 표시 경계에서 번역하며, 번역을 이유로 UI나 싱글턴 의존성을 강제하지 않는다.
- 사용자 작성 이름·콘텐츠, 경로, 직렬화 키와 코드·리소스 식별자는 원래 의미를 보존한다.
  개발자 전용 로그·외부 도구 오류 원문·규격 기호는 유지할 수 있으며,
  이를 둘러싼 사용자 안내 문구에는 로캘 키를 적용한다.

### InputManager와 UI 문맥의 역할

- 애플리케이션의 키·마우스 상태, 보조 키, 위치·이동량·휠, 단축키와 사용자 정의 드래그는
  InputManager의 API 또는 이를 호출하는 기존 래퍼·매크로로 처리한다.
  개별 패널·카메라·도구에서 ImGui::IsKey*·IsMouse*·GetMousePos나
  ImGuiIO의 키·마우스 상태를 읽어 별도의 입력 기준을 만들지 않는다.
- SDL·OS 입력 상태 직접 조회는 InputManager와 플랫폼 백엔드의 입력 수집 경계로 한정한다.
  플랫폼 이벤트를 ImGui 백엔드에 전달하는 경로는 유지하며, 외부 위젯·기즈모 내부 입력까지 재구현하지 않는다.
- ImGui 버튼·메뉴·입력 위젯의 반환값과 호버·포커스·활성 상태는 UI 의미 판정에 사용한다.
  WantTextInput 등 입력 문맥을 함께 확인하여 텍스트 편집·팝업·드래그 중의 단축키 충돌을 방지한다.
- 필요한 기능이 없으면 InputManager를 확장하고 소비자는 그 경로를 사용한다.
  입력은 정해진 프레임 경계에서 한 번 갱신하고 Editor와 PIE가 같은 샘플을 재사용한다.
  화면 좌표·창 내부 좌표·논리 좌표를 구분하고 분리 창·DPI·상대 마우스 모드의 영향을 고려한다.

### 완료와 리뷰에서 확인할 사항

- AuditLocalization의 엄격 검사와 CSV→JSON 변환으로 누락 키·빈 번역·중복을 확인한다.
  번역 서식 인자의 일치와 동적 표시 문구·선택 항목 배열·알림 경로는 별도로 검토한다.
- 언어 변경 시 표시·ID·편집 상태 유지와 입력 포커스·단축키 충돌을 확인한다.
  입력 변경에 해당하면 짧은 누름·해제, 좌우 보조 키, 드래그·휠, 분리 창과 PIE도 검증한다.
- 정적 확인·자동 테스트·실제 UI 조작 결과를 구분하고, 예외와 미검증 범위를 기록한다.
  이 기준 자체를 파일 수정이나 검증 명령 실행의 허가로 해석하지 않으며 AGENTS.md의 작업 방식을 따른다.
