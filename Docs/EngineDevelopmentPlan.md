## 1. 목표와 문서의 역할

Editor에서 제작한 콘텐츠를 PIE와 Client에서 같은 규칙으로 실행할 수 있도록 엔진 기능을 확장한다.
기능 이름이나 편집 패널만 추가하는 것이 아니라 데이터·실행 상태·업데이트·렌더링·저장·실패 처리를 연결한다.
나이아가라를 참고한 모듈형 파티클, 스플라인, 게임용 레이캐스터, 트레일, 2D·3D 애니메이션,
애니메이션 상태 그래프와 스크립트 시스템을 개발 목표에 포함한다.
게임뿐 아니라 강화학습 시뮬레이터와 V-Tuber 제작을 동등한 최종 활용 목표로 둔다.
사용자 결정에 따라 V-Tuber 범위에는 3D와 2D 아바타 실행·추적·방송뿐 아니라 모델·리깅 제작 도구도 포함한다.
각 결과물은 공통 엔진을 사용하되 제작 도구·학습기·추적 장치·방송 연동을 선택 가능한 모듈로 구성한다.
Editor와 인게임 UI에서 그래픽 등 사용자 실행 설정을 조회·검증·적용·저장할 공통 경로를 제공한다.
런타임 설정의 책임·저장 범위와 적용 정책은 19절에서 관리한다.

이 문서는 Engine의 실행 계약과 선행 조건을 관리한다.
문서 간 작업 선택은 통합 우선순위 계획을 따르고, 이 문서의 12절·18절은 해당 기능과 결과물 내부의 순서로 유지한다.
새 기능은 기능 소유 위치와 에셋·실행·GPU·편집 상태를 구분해 배치한다. 전체 폴더 이관을 구현의 선행 조건으로 두지 않는다.
Inspector·전용 패널·콘텐츠 브라우저의 열기·검색·썸네일은 ImGui 개발 계획에서,
공통 RHI·배칭·Compute 실행 등은 렌더링 개발 계획에서 상세화한다.
기존 ImGui 계획 15절의 파티클·스플라인 목표를 이어받으며, Engine 구현과 Editor 작업 흐름이 따로 동작하지 않게 연결한다.

아래 이름과 구성은 계획이다. 새로운 API·컴포넌트·파일 포맷이 이미 존재하거나 구현 방향이 모두 확정됐다는 뜻은 아니다.
이번 작업의 변경 범위는 개발 계획 문서이며, C++ 구현·빌드·테스트·성능 측정은 수행하지 않는다.

## 2. 현재 코드에서 확인한 출발점

다음은 2026-10-24 작업 트리의 관련 소스 정적 확인 결과다. 미커밋 변경을 포함하며 실행 검증 결과가 아니다.

- **레이캐스트 기반은 있다.** `Collision`에 Rect·Box·Sphere·Triangle·Mesh·Terrain 대상 `Raycast()`와 일부 `Sweep()`가 있다.
  `PickingManager`에는 화면 좌표에서 Ray 생성과 씬의 메시·스프라이트를 검사하는 `PickEntityByRay()`가 있다.
  이 선택 경로는 가시성·렌더러 조건을 사용하므로, 렌더링과 무관한 충돌체 질의의 완성으로 취급하지 않는다.
- **스프라이트 표시 기반은 있다.** `Sprite`에 텍스처·영역·피벗이 있고 `SpriteRendererComponent`와 `SpriteRenderSystem`이 있다.
  확인한 제출 경로는 `Simple` 모드의 단일 스프라이트를 처리한다. 전용 프레임 시퀀스 재생 시스템은 이번 검색에서 확인하지 못했다.
- **애니메이션 데이터 기반은 있다.** `Animation`에 위치·회전·스케일 키와 길이·TicksPerSecond가 있고,
  `Skeleton`·`Bone`·`Model`에 골격·계층·애니메이션 참조가 있다.
  `Scene::InstantiateModel()`은 스켈레톤 또는 애니메이션이 있는 모델에 `NotImplemented`를 반환한다.
  스키닝 명령 자료형의 존재만으로 클립 재생·포즈 평가·씬 배치의 연결 완료를 판단하지 않는다.
- **로직 그래프 실행 기반은 있다.** `GraphExecutor`에 Start/Update 진입, 상태·예산·일시정지·단계 실행·추적이 있다.
  현재 `Load()`는 Object 핀을 거부하며, 지원하는 자유/static 함수와 기본 로직 노드를 실행한다.
  `GraphBindingComponent`에 파일 경로와 enabled가 있지만, 확인한 Engine Runtime·System·World와 Client 코드에서는
  이를 읽어 엔티티마다 그래프를 구동하는 연결을 찾지 못했다.
- **그래프 파일 저장 API도 있다.** `GraphFile.h/.cpp`의 JSON 저장·로드를 재사용 대상으로 삼는다.
  GraphFoundation·GraphExecution 문서에는 해당 작업 당시 저장·PIE 연결을 제외했다는 설명이 남아 있으므로,
  문서의 과거 범위와 현재 API의 존재를 구분한다. 저장 API 존재가 PIE 연결의 완료를 뜻하지는 않는다.
- **Script 리소스 틀은 있다.** `Resource/Script`의 `Script`는 생성·초기화·해제 기반이며,
  확인한 파일에는 소스 실행·VM·객체별 인스턴스·엔진 이벤트 바인딩이 없다.
  C++ 프로젝트 모듈·리플렉션 함수·Visual Scripting과 텍스트 스크립트 실행을 같은 완료 항목으로 묶지 않는다.
- 파티클·스플라인·트레일·애니메이션 상태 머신의 전용 실행 시스템은 이번 Engine·Editor 소스 검색에서 확인하지 못했다.
  별도 명칭이나 외부 모듈의 구현 여부는 각 작업을 재개할 때 다시 확인한다.
- `SystemManager`에 FixedUpdate·Update·LateUpdate·제출 단계가 있다.
  각 신규 기능은 어느 단계에서 어떤 데이터를 읽고 쓰는지 정한 뒤 기존 실행 루프에 연결한다.
- `Runtime::Initialize()`는 현재 RHI 초기화 정보를 요구하고 렌더러·오디오를 함께 생성한다.
  `FixedUpdate(dt)`와 `Render(dt)` 호출은 분리돼 있지만, 렌더러 없는 초기화나 환경별 reset/step API가 구현됐다는 뜻은 아니다.
  Runtime과 여러 관리자가 싱글턴이며 활성 Scene 전체를 갱신하므로, 여러 학습 환경의 상태 격리를 별도로 검증해야 한다.
- RHI에 `ReadTexturePixel()`이 있지만 전체 관측 이미지의 비동기 읽기·배치 센서·방송 공유 텍스처의 완료 근거는 아니다.
  확인한 모델 임포트 경로의 뼈 처리만으로 VRM·표정 모프·2D 변형·추적 입력을 지원한다고 판단하지 않는다.
- UI·입력·오디오·리소스·씬 관리의 추가 확인 범위와 확장 목표는 14절에 기록한다.
  강화학습·V-Tuber 관련 전용 API·모듈은 이번 관련 소스 검색에서 확인하지 못했으며, 각 단계 시작 시 다시 확인한다.

## 3. 공통 구현 기준: 상태·시간·저장·성능

- 공유할 에셋 정의와 인스턴스별 실행 상태를 분리한다.
  같은 클립·효과·그래프를 사용하는 두 엔티티의 재생 시간·변수·난수·입자 목록이 섞이지 않게 한다.
- 실행 상태는 대상 Scene·엔티티·실행 세션의 수명에 연결한다. PIE 시작·종료·재시작과 씬 교체 시 정리 책임을 정한다.
  Editor 미리보기도 같은 평가 코드를 쓰되 원본 씬·게임 이벤트와 분리된 실행 문맥을 사용한다.
- delta의 단위, 고정/가변 스텝, 타임 스케일, 일시정지·한 스텝, 큰 delta의 처리 정책을 정한다.
  패널이나 렌더 제출 횟수에 따라 게임 상태가 중복 갱신되지 않게 한다.
- 충돌 질의, 상태 전이, 애니메이션 평가, Transform 갱신, 효과 업데이트, 렌더 제출의 읽기·쓰기 순서를 정의한다.
  이벤트 중 엔티티 생성·삭제와 컴포넌트 변경은 반복 중인 저장소와 충돌하지 않도록 적용 시점을 정한다.
- 설정·참조는 기존 Reflection/Archive·리소스 핸들 경로로 저장한다.
  일반 등록 타입마다 포맷별 수동 저장 함수를 추가하지 않고, 필요한 참조 의미만 확장 지점에서 처리한다.
  원시 객체 포인터·GPU 자원·VM 내부 주소는 영속 식별자로 사용하지 않는다.
- 에셋 버전·기본값·누락 필드·지원 중단과 참조 실패를 정의한다.
  지원하는 JSON·바이너리의 데이터 의미를 맞추고, 미지원 형식을 성공으로 처리하지 않는다.
- 프레임별 객체 수·작업 수·임시 할당·CPU 시간·GPU 시간·메모리·업로드량의 비용을 측정한다.
  풀·캐시·배칭은 실제 반복 비용과 측정 근거에 맞춰 적용하고, 개수·용량·대기열에 상한을 둔다.
- Engine의 실행 기능은 ImGui나 Editor 선택 상태에 의존하지 않는다.
  고정 표시 문구·리플렉션 표시명·오류 안내는 기존 로캘 키와 영어·한국어 번역을 함께 준비한다.
  입력이 필요한 호출자는 InputManager를 사용하고, 실행 시스템은 가능한 한 해석된 액션·명령·값을 받는다.

## 4. 나이아가라를 참고한 모듈형 파티클 시스템

목표는 여러 이미터와 재사용 모듈·파라미터로 효과를 제작하고 런타임에서 제어하는 것이다.
Niagara의 System·Emitter·Module 구성을 기능 참고로 삼는다.
[Epic Games Niagara 개요](https://dev.epicgames.com/documentation/en-us/unreal-engine/overview-of-niagara-effects-for-unreal-engine),
[주요 개념](https://dev.epicgames.com/documentation/unreal-engine/key-concepts-in-niagara-effects-for-unreal-engine).
Niagara 에셋 호환이나 같은 수준의 기능 전체 구현을 초기 완료 조건으로 삼지 않는다.

### 1단계: 단일 CPU 이미터

- 생성률·버스트·최대 수·수명·초기 위치·속도·색·크기·회전·텍스처와 고정 난수 시드를 지원한다.
- 로컬/월드 시뮬레이션 공간과 소유 엔티티 이동·비활성화·삭제의 의미를 정한다.
- 생성·갱신·소멸을 처리하고 재생·정지·방출 중지 후 잔여 입자 소멸·즉시 제거·초기화를 구분한다.
- 첫 렌더러는 스프라이트로 제한해 기존 제출 경로를 검토한다.
  파티클마다 엔티티·드로 호출을 만드는 방식의 비용을 측정하고, 필요한 입자 배칭을 렌더링 계획과 연결한다.
- 최대 개수와 예열 스텝·시간을 제한하며, CPU 시뮬레이션과 투명 오버드로·정렬·GPU 비용을 따로 측정한다.

### 2단계: 효과 에셋·다중 이미터·모듈

- 여러 이미터를 효과 에셋에서 조합하고, 인스턴스마다 독립된 실행 상태를 둔다.
- 생성·갱신 단계에 초기화·힘/가속도·수명별 색/크기·감쇠·소멸 등 실제 필요한 모듈부터 등록한다.
  모듈 순서·입출력 속성·타입·기본값과 호환성을 검증한다.
- 효과 공통값·이미터값·입자 속성·외부 노출 파라미터의 소유자와 갱신 빈도를 구분한다.
- 게임 코드·그래프·스크립트에서 위치·색·방출량·목표 등을 전달하고, 누락되거나 잘못된 타입의 파라미터를 보고한다.
- 충돌·생성·사망 이벤트는 개수와 재귀 생성에 예산을 둔다. 자식 효과의 무제한 연쇄 생성은 제한한다.

### 3단계: 그래프 제작·렌더러 확장·GPU 실행

- 모듈 스택의 기능이 검증된 뒤 필요하면 노드로 파라미터·모듈 연산을 제작한다.
  기존 Graph의 편집 데이터·메타데이터를 재사용할 수 있는 범위를 검토하되, 입자마다 일반 Logic 실행기를 구동하는 것을 기본으로 삼지 않는다.
- 메시·리본 등 추가 렌더러와 스프라이트 시트 애니메이션을 실제 콘텐츠 요구에 따라 연결한다.
- GPU 시뮬레이션은 Compute 실행·버퍼·동기화·기능 지원 조회가 준비된 뒤 별도 경로로 추가한다.
  CPU와 GPU의 지원 모듈·이벤트·충돌 차이를 명시하고, 매 프레임 GPU 전체 상태를 CPU로 읽어오지 않는다.
- 거리·화면 기여도·품질 단계별 방출량·갱신 빈도·시뮬레이션 중지 정책과 경계를 정한다.
  화면 밖 동작을 생략했을 때 재등장·시간 진행 결과도 검증한다.

완료 예제: 하나의 효과가 섬광·불꽃·연기를 조합하며, 엔티티마다 색·강도를 다르게 재생한다.
저장·재실행·PIE 반복·Client 실행 후 파라미터와 종료 동작이 일치하고, 정한 입자 수·메모리·프레임 예산을 지킨다.

## 5. 스플라인 데이터·평가·경로 활용

- 첫 용도를 오브젝트 또는 카메라의 경로 이동으로 정하고, 지원 곡선·제어점·접선·열림/닫힘과 좌표계를 명시한다.
- 위치·접선 평가와 구간 선택부터 구현하고, 점 없음·한 점·중복점·길이 0·끝점·루프 경계의 결과를 정의한다.
- 일정 속도 이동이 필요하면 호 길이 근사·거리 기반 평가를 추가한다.
  매개변수의 일정 증가와 거리의 일정 증가를 구분하고, 오차·분할 수·캐시 크기를 제한한다.
- 경로 추종에서 속도·반복·역방향·시작 오프셋을 지원한다. 방향 정렬에는 up 기준·접선 퇴화·비틀림 정책을 정한다.
- 독립 에셋과 씬 컴포넌트 중 재사용 요구에 맞는 저장 단위를 선택한다.
  런타임 평가·Editor 기즈모·썸네일이 같은 데이터 해석을 사용한다.
- 제어점·관련 Transform 변경 시에만 필요한 캐시를 갱신한다. 부모 변환·비균일 스케일이 거리 평가에 주는 영향을 검증한다.
- 도로·케이블·스플라인 메시 변형은 경로 평가 이후의 별도 기능이다. 스플라인 구현만으로 형상 생성까지 완료 처리하지 않는다.

완료 예제: 저장한 경로를 Editor에서 수정하고, 같은 오브젝트가 PIE와 Client에서 지정 속도로 이동한다.
끝점·루프·부모 변환·실행 중 경로 변경에서 위치·방향·캐시 갱신이 정한 계약과 일치한다.

## 6. 게임용 레이캐스터와 씬 충돌 질의

- 기존 `Collision::Raycast()`를 재사용하면서 질의 대상 Scene을 명시하는 게임용 진입점을 만든다.
  발사체·시선·상호작용·접지 등에서 사용할 수 있도록 Collider를 기준으로 조회한다.
  Editor 피킹·UI 히트 테스트·물리 질의의 공통 수학과 서로 다른 대상·필터 정책을 구분한다.
- 시작점·방향·최대 거리·좌표계·정규화 규칙과 잘못된 입력의 결과를 정의한다.
  2D와 3D에서 지원하는 형상·평면·회전·스케일의 범위를 명시한다.
- 처음에는 최근접 충돌을 지원하고, 이후 충돌 유무만 확인·모든 충돌·사용자 버퍼 결과를 요구에 따라 추가한다.
  레이어/마스크·Trigger 포함 여부·자기 자신 제외·비활성 충돌체·시작점이 내부인 경우·동일 거리의 순서 정책을 정한다.
- 결과에 유효한 엔티티/충돌체 식별자·거리·점·법선을 제공하고, 메시 질의의 삼각형·barycentric 등은 지원 범위를 구분한다.
  기존 `HitResult`의 범용 `userData` 포인터를 장기 보관 가능한 참조로 취급하지 않는다.
- 메시 정밀 판정과 단순 Collider 판정의 비용·의미를 구분한다.
  메시 BVH가 있어도 씬 전체의 후보 조회 비용은 남으므로, 정적/동적 후보 수를 측정한 뒤 공간 색인을 추가한다.
- 이동·형상 수정·삭제에 따른 가속 구조 갱신과 질의 중 변경의 시점을 정한다.
  나중에 Sweep·Overlap을 공통 씬 질의로 확장하되 기존 일부 도형 `Sweep()`를 씬 기능 전체의 완료로 보지 않는다.
- 게임 입력으로 Ray를 만드는 호출부는 기존 InputManager와 카메라 변환을 사용한다.
  물리 질의 자체는 마우스·현재 뷰포트·화면 표시 여부에 의존하지 않는다.

완료 예제: 화면에 보이지 않는 충돌체도 지정 레이어에 따라 맞히고, 자기 자신·Trigger·거리 제한을 의도대로 처리한다.
무충돌·내부 출발·접선·거리 0·비균일 스케일·대상 삭제와 대량 질의의 정확성·비용을 검증한다.

## 7. 트레일·리본 이펙트

- 첫 단계는 움직인 경로의 샘플을 이어 만드는 트레일이다.
  최소 거리/시간·최대 점 수·유지 시간·폭/색 곡선·UV·머티리얼·방출 on/off를 정의한다.
- 샘플은 실행 인스턴스가 소유하고, 고정 상한의 버퍼나 풀을 사용한다.
  정지 시 중복점·큰 delta·순간이동·씬 전환에서 비정상적으로 긴 삼각형이나 무제한 샘플이 생기지 않게 한다.
- 카메라 기준 리본과 명시적 방향 기준을 구분한다. 꺾임·겹친 점·접선 퇴화·정렬·경계 갱신을 처리한다.
  다중 뷰포트에서는 시뮬레이션 샘플을 중복 갱신하지 않고 뷰별 표현만 필요한 범위에서 계산한다.
- 동적 정점/인덱스 업로드와 투명 오버드로·드로 호출 수에 예산을 둔다.
  렌더링이 사용하는 버퍼의 프레임 수명과 재사용 동기화를 확인한다.
- 검 궤적처럼 두 소켓/끝점의 이력을 잇는 방식은 골격·소켓 기반 이후에 확장한다.
  파티클 리본과 공유할 수 있는 메시 생성은 재사용하되 독립 트레일의 사용에 파티클 전체를 강제하지 않는다.
- 스플라인은 정의한 곡선이고 트레일은 시간에 따른 이동 이력이라는 차이를 유지한다.
  필요한 샘플링·선분 생성만 공유하고, 트레일 구현에 스플라인 전체를 선행 조건으로 만들지 않는다.

완료 예제: 이동체 잔상 또는 무기 궤적이 방출 중지 후 자연스럽게 소멸한다.
정지·급회전·순간이동·재생 초기화·PIE 반복에서 모양과 버퍼 수명이 안정적이며 최대 점 수를 지킨다.

## 8. 스프라이트 애니메이션과 Flipbook (SpriteAnimation)

- **구현 완료 (2026-11-01)**:
  - 독립 에셋 `SpriteAnimation` 클래스를 구축하여 클립(프레임 시퀀스, 가중치 `duration`, 기본 FPS, `ESpriteAnimationPlayMode`)을 에셋 단위로 분리하고 여러 엔티티가 공유 가능하도록 구조화.
  - 리플렉션-아카이브 자동 직렬화 파이프라인과 완벽히 연동하여 Zero-Boilerplate 기반 JSON(`.spriteanim`) 저장 및 복원 지원.
  - `SpriteAnimationComponent`와 `SpriteAnimationSystem`에 에셋 우선 및 로컬 폴백을 연결하고, 프레임 스파이크 방지(상한 2바퀴 컷오프) 및 프레임별 지속시간 가중치 평가 구현.
  - `SpriteAnimationEditor` 전용 저작 도구를 구축하여 실시간 2D 프리뷰(체크무늬 배경, 줌/팬, 피벗 크로스헤어), 재생 툴바, 프레임 순서/가중치 편집 및 하단 필름스트립 타임라인 완성. 콘텐츠 브라우저 더블클릭 연동 완료.
- 클립은 공유하고 현재 시간·프레임·재생 상태는 엔티티별로 관리한다.
  공유 Sprite의 영역을 매 프레임 수정해 다른 엔티티의 표시까지 바꾸지 않는다.
- 누적 시간으로 프레임을 계산하고 낮은 FPS·큰 delta에서도 속도를 유지한다.
- 클립과 재생 설정을 저장·복원하고 Inspector에서 재생·미리보기·프레임 편집을 연결한다.
  파티클 Flipbook도 가능한 데이터·평가 규칙을 재사용하되 입자마다 불필요한 엔티티를 만들지 않는다.

완료 예제: 같은 클립을 두 엔티티가 서로 다른 속도와 시작 시간으로 재생하고, 저장·복원·일시정지·낮은 FPS에서 결과가 일치한다.

## 9. 애니메이션 재생·포즈 평가·스키닝

### 1단계: 클립 재생과 Transform/속성 트랙

- 기존 Animation의 시간 단위를 초로 해석하는 경계와 TicksPerSecond가 0인 입력의 정책을 정한다.
- 위치·스케일 보간과 회전 보간, 키 없음·단일 키·중복 시간·끝점·반복·재생 속도·스크러빙을 정의한다.
- 클립 데이터와 플레이어 상태를 나누고, 바인딩할 대상 엔티티/속성의 유효성을 검사한다.
  일반 속성 트랙은 기존 뼈 이름 기반 트랙과 대상 식별 의미가 다르므로 필요한 데이터 확장을 명시한다.
- 게임 코드·그래프·애니메이션·물리가 같은 Transform을 덮어쓸 때의 소유권과 적용 순서를 정한다.

### 2단계: 골격 포즈와 스키닝 연결

- 클립의 뼈 트랙을 Skeleton에 매핑하고 로컬 포즈→계층 월드 포즈→스키닝 행렬의 좌표계·순서를 검증한다.
- 바인드 포즈·역바인드 행렬·루트 변환·축/단위 변환과 뼈별 가중치의 지원 범위를 정한다.
  모델 배치의 현재 `NotImplemented` 경로를 실제 컴포넌트·시스템·렌더 제출로 연결한다.
- 재생 인스턴스마다 포즈·행렬 수명을 소유하고, 렌더 명령의 행렬 참조가 사용 종료 전에 해제·변경되지 않게 한다.
- 뼈 버퍼 업로드와 셰이더 바인딩은 기존 RHI와 BINDING_LAYOUT의 스키닝 그룹을 대조해 연결한다.
  지원 백엔드·그림자·피킹·경계와 컬링에서 애니메이션된 형상을 처리하는 범위를 함께 명시한다.

### 3단계: 블렌딩과 게임 연결

- 두 클립 전이·블렌딩부터 검증하고, 이후 레이어·가중치·마스크·가산 애니메이션·동기화를 확장한다.
- 애니메이션 이벤트·소켓을 효과·오디오·무기 부착에 연결한다.
  Root Motion은 루트 이동 추출·적용·물리 이동과의 책임 및 반복 경계가 준비된 뒤 별도 지원한다.
- IK·제약·리타게팅·표정/모프는 기본 재생·스키닝 이후의 확장 목표로 둔다.
- 키 탐색·평가·포즈 버퍼 재사용·GPU 업로드량을 측정하고, 비가시 객체의 갱신 제한과 게임 이벤트 보존 정책을 정한다.

완료 예제: 임포트한 캐릭터가 바인드 포즈와 단일 클립을 올바르게 표시하고, 이후 Idle/Walk 전이가 부드럽게 동작한다.
동일 클립의 다중 인스턴스·골격 불일치·누락 트랙·음수/큰 delta의 지원 정책과 PIE·Client 결과를 확인한다.

## 10. 그래프 상태 로직으로 애니메이션 제어 (상세 계획: [AnimatorGraphPlan.md](AnimatorGraphPlan.md))

- 상세 아키텍처 및 단계별 로드맵(Phase 1~5)은 [AnimatorGraphPlan.md](AnimatorGraphPlan.md)를 따른다.
- 상태·클립·전이 조건·전이 시간·우선순위·초기 상태와 Bool/Float/Int/Trigger 파라미터를 정의한다.
  그래프 에셋은 공유하고 현재 상태·전이 진행·파라미터·이벤트 큐는 실행 인스턴스마다 소유한다.
- 먼저 Idle↔Walk 같은 단순 상태 머신으로 2D 또는 3D 플레이어를 제어한다.
  2D와 3D의 상태/전이 계약이 실제로 같으면 재사용하고, 프레임 선택과 포즈 블렌딩까지 같은 평가기로 강제하지 않는다.
- 같은 스텝의 다중 전이·자기 전이·Trigger 소비·조건 순환·전이 중 새 전이·종료 시간과 시간 단위를 명시한다.
  상태 진입/갱신/종료 이벤트가 어느 시점에 몇 번 발생하는지 정하고, 한 스텝의 전이 횟수에 제한을 둔다.
- 게임 로직 또는 스크립트가 파라미터를 갱신하고 상태 머신이 클립 재생을 결정한다.
  애니메이션 이벤트가 다시 파라미터를 변경할 때의 재진입·다음 스텝 반영 정책을 정한다.
- 상태 전이 그래프와 포즈를 조합하는 Blend Graph는 다른 평가 요구다.
  기존 Logic 그래프의 UI·식별자·직렬화 기반을 검토하되 현재 Logic/Shader 도메인에 이름만 추가해 실행 완료로 처리하지 않는다.
  초기 상태 머신에 일반 그래프 VM 전체가 반드시 필요한 것은 아니다.
- 현재 상태·활성 전이·입력 파라미터·전이 사유를 디버깅하고, 잘못된 상태·클립·조건 참조를 저장/로드와 실행 전에 검사한다.
- 이후 중첩 상태·서브 그래프·Blend Tree·레이어를 실제 중복과 콘텐츠 요구가 확인된 범위에서 추가한다.

완료 예제: 게임 속도 파라미터와 점프 Trigger로 Idle/Walk/Jump를 제어하고, 같은 데이터가 PIE와 Client에서 같은 전이를 만든다.
누락 클립·동시 전이·Trigger 반복·일시정지·상태 초기화와 다중 캐릭터의 독립 상태를 검증한다.

## 11. 스크립트 시스템과 Visual Scripting 실행 연결

### A. 실행 계약과 기존 그래프의 씬 연결

- 엔티티별 인스턴스와 생성·시작·Update·FixedUpdate·비활성화·파괴의 이벤트를 정의한다.
  실제 지원 이벤트부터 연결하고, 컴포넌트 제거·씬 교체·PIE 종료에서 등록한 콜백·타이머를 정리한다.
- 기존 GraphBindingComponent·GraphFile·GraphExecutor를 활용해 Logic 그래프의 엔티티별 실행을 연결한다.
  Start/Update를 호출할 시스템·순서·실행 예산과 엔티티 삭제 시 동작을 먼저 정한다.
- Object 접근은 Scene 문맥·유효한 엔티티 핸들·허용된 컴포넌트/함수 바인딩을 준비한 뒤 확장한다.
  raw 포인터를 스크립트나 그래프에 장기 노출하지 않고, 삭제·씬 변경·지연 호출 시 유효성을 확인한다.
- 입력 액션·Raycast·애니메이션 파라미터·효과 재생을 실제 게임 예제에 필요한 API부터 노출한다.
  리플렉션에 등록됐다는 이유로 저장·호출·쓰기 권한을 모두 허용하지 않는다.

### B. 텍스트 스크립트

- 텍스트 스크립트 실행을 명시적 개발 목표로 둔다. 언어·VM·외부 라이브러리는 아직 선택하지 않는다.
  바인딩·빌드/배포 의존성·디버깅·중단/실행량 제한·메모리 관리와 학습 비용을 비교한 뒤 정한다.
- Script 리소스에는 소스 또는 실행 산출물과 버전·참조 정보를 연결하고, 실행 인스턴스의 변수·VM 상태와 분리한다.
- 사용자가 작성한 필드를 Inspector에서 편집하고, 지원 타입·기본값·리소스/엔티티 참조를 공통 직렬화에 연결한다.
- 컴파일/로드·바인딩·실행 오류를 구분하고 파일·행 또는 그래프 노드·함수 문맥으로 보고한다.
  한 스크립트 실패가 전체 게임 루프를 중단할지 해당 인스턴스만 중지할지 정책을 명시한다.
- 파싱·컴파일과 바인딩 조회를 매 프레임 반복하지 않는다. 호출 비용·할당·GC·대량 인스턴스의 지연을 측정한다.
  실행 예산이 네이티브 함수 내부의 무한 루프나 블로킹을 선점한다고 가정하지 않는다.

### C. 재로딩·확장·배포

- 처음에는 재시작으로 새 코드를 적용해도 된다. 핫 리로드는 새 코드 검증·교체·상태 이전·실패 복구를 별도 단계로 구현한다.
- 외부 수정 실패 시 기존 실행 가능한 버전을 유지하고, 유지할 필드·초기화할 상태·타입 변경의 호환성을 정의한다.
- Visual Scripting과 텍스트 스크립트는 엔진 API·엔티티 수명 계약을 공유할 수 있지만, 실행기·컴파일러를 무조건 통합하지 않는다.
- C++ 프로젝트 모듈·플러그인과 스크립트 실행의 지원 범위를 별도로 기록한다.
  네이티브 모듈을 내릴 때는 객체·콜백·함수 바인딩·그래프 참조를 먼저 정리한다.
- 필요한 런타임·스크립트/실행 산출물·의존 에셋을 패키징하고 Editor 없이 실행한다.

완료 예제: 엔티티에 붙인 로직이 입력 액션으로 이동하고, Raycast로 상호작용하며, 상태 파라미터와 파티클 재생을 제어한다.
같은 스크립트/그래프의 두 인스턴스가 상태를 공유하지 않고, 오류·삭제·씬 교체·재실행에서도 참조와 콜백이 남지 않는다.

## 12. 권장 진행 순서와 의존 관계

전체 공통 기반·렌더링·Editor·결과물별 작업의 선택은 [DevelopmentPriorities.md](DevelopmentPriorities.md)를 따른다.
Client 시작 설정과 배포는 BuildAndPackagingPlan의 기존 보류 상태를 유지하며, 아래 순서가 이를 자동 재개하지 않는다.

기존 편집 데이터 보호·리소스 참조·배포 목표를 유지하면서 아래 기능을 작은 예제로 완성한다.
이 순서는 고정 일정이 아니며 모든 기능을 앞 항목 전체 완료 후에만 시작해야 한다는 뜻도 아니다.
아래는 기존 게임 기능의 진행 순서다. 전체 최종 목표의 진행은 18절을 함께 따르며,
강화학습·V-Tuber 시작을 GPU 파티클·멀티플레이 등 게임 기능 전체의 완료 뒤로 미루지 않는다.

1. 실행 인스턴스·시간·엔티티 수명·측정 기준을 정리한다. 각 기능은 공통 기반의 실제 필요한 부분만 추가한다.
2. 기존 충돌 수학을 게임용 씬 Raycast에 연결하고, 스프라이트 애니메이션을 작은 실행 예제로 완성한다.
3. 단일 CPU 파티클·독립 트레일·스플라인 경로를 서로 불필요한 의존성 없이 구현한다.
4. 애니메이션 클립 평가→골격/스키닝→두 클립 블렌딩을 검증한다. 상태 머신의 첫 적용은 2D 재생기에도 가능하다.
5. 단순 애니메이션 상태 머신과 기존 Logic 그래프의 엔티티 실행 연결을 각각 완성하고, 게임 파라미터로 연결한다.
6. 파티클을 다중 이미터·모듈·외부 파라미터로 확장한다. 검 궤적은 골격 소켓이 준비되면 연결한다.
7. 텍스트 스크립트의 언어/VM을 선택해 같은 엔진 API·수명 계약에 연결한다.
8. 콘텐츠 요구와 측정 결과에 따라 GPU 파티클·포즈 그래프·고급 애니메이션·핫 리로드를 확장한다.

핵심 선행 조건:

- GPU 파티클 → Compute·버퍼·동기화·지원 조회와 GPU 계측.
- 애니메이션 상태 제어 → 검증된 클립 플레이어. 포즈 블렌딩 → 골격 포즈 평가.
- 무기 소켓 트레일 → 골격 포즈/소켓. 일반 이동체 트레일은 먼저 구현할 수 있다.
- 스크립트/그래프의 씬 객체 접근 → 엔티티 유효성·수명·허용 API·변경 적용 시점.
- 콘텐츠 브라우저의 타입별 썸네일 → 실제 타입 식별·읽기·제한된 미리보기 실행과 캐시.
- 학습 환경 → 외부 제어 스텝·초기화·관측/행동 계약·상태 격리. 고급 게임 AI나 텍스트 스크립트 전체는 필수 선행 조건이 아니다.
- 3D V-Tuber → 스키닝·표정 모프·휴머노이드 매핑·추적 입력. 강화학습 완료는 필수 선행 조건이 아니다.
- 2D V-Tuber → 변형 메시·파라미터 평가·마스크/합성·추적 매핑. 3D 아바타 전체의 완료를 요구하지 않는다.
- 모델·리깅 제작 도구 → 편집용 원본 데이터·Undo/Redo·안전한 저장과 런타임 데이터 변환.

## 13. 기능 완료와 성능 검증

- [ ] 작은 예제에서 제작→저장→재실행→PIE 시작/종료→Client 실행을 확인한다.
- [ ] 에셋은 공유하면서 실행 인스턴스의 상태는 독립적으로 유지된다.
- [ ] 씬 교체·엔티티 삭제·컴포넌트 제거·미리보기 종료에 상태·작업·콜백·GPU 자원이 정리된다.
- [ ] 일시정지·한 스텝·낮은 FPS·큰 delta·잘못된 입력·누락 참조에서 정한 정책대로 동작한다.
- [ ] 지원하는 JSON·바이너리의 저장 의미가 일치하고, 손상·미지원 버전을 성공으로 처리하지 않는다.
- [ ] Editor 미리보기와 PIE·Client의 평가 규칙이 일치하며 원본 편집 데이터가 보존된다.
- [ ] UI·리플렉션 표시명·오류 안내의 로캘과 InputManager 사용을 각 기능의 구현에 포함한다.
- [ ] 기준 장비·해상도·빌드 구성·콘텐츠 수를 기록하고 CPU/GPU 구간·p95/p99 프레임 시간·메모리·할당·업로드를 측정한다.
- [ ] 입자 수·트레일 점 수·질의 수·캐릭터/뼈 수·스크립트/그래프 인스턴스를 늘리며 비용과 상한 동작을 확인한다.
- [ ] 비동기·캐시·컬링·저빈도 갱신의 성능과 생략으로 바뀌는 이벤트·시간 진행·화질을 함께 검증한다.
- [ ] 사용자 수행 빌드·자동 검사·Editor 조작·GPU 출력·성능 측정 결과를 구분해 구현 기록에 남긴다.

수치 예산은 각 기능의 첫 구현 전에 기준 예제로 확정하고 결과에 따라 갱신한다.
소스 존재·문서 작성·일부 검사 통과를 모든 플랫폼·런타임·성능 검증 완료로 일반화하지 않는다.

## 14. 다른 엔진의 기본 제작 기능과 비교한 추가 모듈

아래는 앞서 조사한 공백을 계획에 편입한 것이다. 기본 내장·공식 패키지·선택 기능의 범위는 엔진마다 다르다.
각 항목은 기반 코드의 존재와 실제 사용 흐름의 완성을 구분하며, 모두를 엔진 핵심의 필수 의존성으로 만들지 않는다.

### A. 게임용 텍스트·UI 위젯

- 현재 Canvas·Image·Button·레이아웃·포인터 이벤트 기반을 확장한다. ImGui의 Editor 텍스트를 게임 UI 구현으로 취급하지 않는다.
- 폰트/글리프 캐시·텍스트 배치·줄바꿈·정렬·fallback·한글을 지원하고, 입력 위젯은 IME 조합·선택·커서·클립보드를 처리한다.
  텍스트·스크롤·슬라이더·체크박스·목록·자동 배치·클리핑과 키보드/게임패드 포커스를 작은 단계로 추가한다.
- 완료 예제: Client에서 한글 메뉴·설정·입력창을 사용하고 해상도·DPI 변경 후에도 배치·포커스가 유지된다.
  글리프 생성·레이아웃 재계산·배칭·캐시 메모리의 비용을 측정한다.

### B. 게임 입력 액션·컨트롤러

- 키보드·마우스 중심 InputManager에 액션·축·입력 문맥·우선순위와 런타임 재바인딩을 연결한다.
- 게임패드 버튼/축·데드존·진동·연결/해제·플레이어별 장치 할당을 추가한다. 터치는 대상 플랫폼 단계에서 확장한다.
- 완료 예제: 같은 Move/Jump 액션을 키보드와 게임패드로 조작하고 바인딩을 저장·복원한다.
  UI·PIE·텍스트 입력 문맥의 충돌을 검사한다. 외부 추적 패킷 수신은 별도 장치 모듈이며 InputManager로 억지로 합치지 않는다.

### C. 물리 시뮬레이션·충돌 이벤트

- 현재 PhysicsSystem은 부모 없는 비회전 2D Box 중심이다. 3D 형상·강체·Joint 컴포넌트 선언을 실제 해결기의 지원으로 해석하지 않는다.
- 회전·다른 형상·3D 강체·마찰·각운동·조인트·CCD·sleeping·공간 후보 검색과 충돌/Trigger Enter·Stay·Exit를 단계적으로 연결한다.
- 2D와 3D를 나누어 자체 구현 범위와 외부 물리 라이브러리 도입을 비교하고, 접촉·관절 정확도와 처리량을 기준 예제로 평가한다.
  강화학습용 관절 제어·접촉 센서는 15절의 실제 과제에 필요한 수준부터 지원한다.
- 완료 예제: 낙하·마찰·반발·Trigger·조인트 예제에서 고정 스텝·낮은 FPS·씬 재시작의 결과와 허용 오차를 확인한다.

### D. 캐릭터 이동

- 접지·경사면·계단·벽 미끄러짐·이동 플랫폼·캡슐 이동 검사를 제공한다. 게임별 점프 규칙은 프로젝트에서 구성한다.
- 이동·물리·애니메이션 Root Motion의 적용 순서와 소유권을 정의한다.
- 완료 예제: 캐릭터가 경사·문턱·움직이는 발판에서 안정적으로 이동하고 순간이동·겹침 복구·큰 delta를 처리한다.
  Raycast 존재만으로 캐릭터 이동이 완료됐다고 판단하지 않는다.

### E. 내비게이션·경로 탐색

- NavMesh 생성/저장·경로 질의·경로 추종·영역/레이어·연결 링크·이동 장애물과 회피를 단계적으로 지원한다.
  격자 기반 과제는 A*부터 시작할 수 있다. 스플라인 경로와 장애물을 피해 찾은 경로를 구분한다.
- 완료 예제: 적이 도달 가능한 목표를 추적하고 경로 없음·막힌 길·목표 이동을 처리한다.
  질의 예산·재탐색 빈도·동시 에이전트 수를 측정한다.

### F. AI 의사결정·인지

- AI 상태 머신·작업·Blackboard·시야/청각 인지부터 검토하고, 실제 복잡성이 생기면 Behavior Tree를 추가한다.
- 애니메이션 상태 그래프와 행동 선택을 구분하며, 학습 정책도 같은 게임 명령 API를 사용할 수 있게 한다.
- 완료 예제: 순찰→발견→추적→공격/복귀 흐름에서 작업 중단·목표 삭제·씬 초기화가 일관되게 동작한다.

### G. 런타임 비동기 로딩·에셋 식별

- ResourceManager의 핸들과 Editor 비동기 임포트는 재사용하되, Client용 요청·진행률·취소·우선순위·중복 공유·실패 전달을 마련한다.
- 이동/이름 변경에도 참조를 해석할 에셋 식별·메타데이터 색인·의존성·로드/언로드 정책을 정한다.
  CPU 읽기/변환과 GPU 업로드를 구분하고 메모리·프레임별 작업량을 제한한다.
- 완료 예제: 로딩 화면을 유지하면서 의존 에셋을 읽고, 실패·취소·재요청에서 기존 리소스와 참조가 보존된다.

### H. 씬 스트리밍·영속 객체

- 현재 복수 Scene 등록 API를 기반으로 비동기 읽기→준비→활성화→비활성화→언로드 계약을 정의한다.
- 씬 사이 참조·영속 객체·씬별 물리/오디오/스크립트 상태와 로드 취소·실패를 처리한다.
  큰 월드 스트리밍과 독립 학습 환경의 격리는 다른 요구이므로 Scene 수가 많다는 이유로 둘 다 지원한다고 판단하지 않는다.

## 15. AI 강화학습 시뮬레이터

### A. 환경 API와 과제 정의

- Engine의 시뮬레이션과 외부 학습기를 분리하고, Python 어댑터의 첫 호환 목표를 Gymnasium으로 둔다.
  `reset(seed, options)`와 `step(action)`의 관측·보상·terminated·truncated·info를 명시한다.
  엔진 C++ API 이름을 Python API와 동일하게 강제하지는 않는다.
- 관측/행동의 shape·dtype·범위·단위·좌표계·버전을 선언하고 값과 NaN/Inf를 검증한다.
  벡터·이산/연속 행동·행동 마스크·관측 누적은 실제 과제에서 필요한 것부터 지원한다.
- 목표 달성/실패에 따른 종료와 시간 제한 등 외부 중단을 구분한다. 수치 오류·통신 실패를 정상 terminal 보상으로 숨기지 않는다.
  최종 관측과 다음 에피소드의 초기 관측이 섞이지 않도록 초기에는 명시적 reset으로 시작한다.
- 사용자는 과제별 초기화·행동 적용·관측·보상 항목·종료 조건을 등록한다.
  엔진은 실행 순서·수명·검사·기록을 담당하며 게임 규칙이나 보상식을 핵심 모듈에 고정하지 않는다.

근거: [Gymnasium Env](https://gymnasium.farama.org/api/env/).
해당 API의 종료·중단 구분과 reset 계약을 따르며, 연결할 학습 라이브러리의 어댑터·버전을 별도 검증한다.

### B. 외부 제어 시간 진행·초기화·헤드리스

- `step` 한 번이 정확히 몇 개의 물리 스텝을 수행하는지 정의한다.
  물리 dt·정책 결정 주기·행동 유지·렌더/센서 주기를 구분하고, 학습 속도를 올리기 위해 물리 dt 자체를 임의로 키우지 않는다.
- 실행 시간은 시뮬레이션 스텝에서 계산하며 실시간 FPS 제한·VSync·대기 시간을 학습 스텝의 조건으로 삼지 않는다.
  현재 Runtime의 호스트 주도 `FixedUpdate(dt)`를 활용하되 TimeManager의 실제 시간 누적과 분리한다.
- Renderer·창·오디오 없는 수치 관측 실행, 표시 창 없는 GPU 센서 렌더, Editor 디버깅 실행을 구분해 초기화한다.
  현재 Runtime의 필수 RHI 조건과 오디오 갱신 의존성을 이 범위에서 최소한으로 조정한다.
- reset은 엔티티·물리 속도·접촉/해결기 상태·타이머·스크립트·그래프·이벤트·난수·센서 누적을 초기화한다.
  씬 Archive만 복원하면 초기화가 끝났다고 가정하지 않는다. 필요한 임시 상태의 별도 복원 계약을 둔다.
- 환경별 난수 스트림·초기 seed·에피소드 번호·물리 설정·엔진/에셋 버전을 기록한다.
  동일 seed의 비트 단위 결정성을 모든 하드웨어에 보장하지 않고 지원 환경과 허용 오차를 측정한다.

참고: [Isaac Lab 환경 설정](https://isaac-sim.github.io/IsaacLab/main/source/api/lab/isaaclab.envs.html)의
물리 시간·정책 주기(decimation)·초기화 구분을 설계 비교에 사용한다. 해당 프레임워크 의존성 도입은 별도 선택이다.

### C. Python 연결·병렬 환경·다중 에이전트

- 첫 연결은 로컬 프로세스의 명시적 요청/응답으로 시작하고, 환경 ID·에피소드 ID·스텝 ID·타임아웃·종료를 정의한다.
  소켓·공유 메모리·직접 C API/Python 바인딩 중 구현·배포 부담과 측정된 복사 비용으로 선택한다.
- 싱글턴 구조를 당장 전면 교체하지 않고 프로세스별 독립 환경부터 검증할 수 있다.
  같은 프로세스의 다중 환경은 Scene별 시간·물리·난수·상태를 명시적으로 격리한 뒤 추가한다.
- 벡터화는 배치 관측/행동·환경별 reset·실패 격리를 지원한다.
  autoreset 모드·최종 관측·버퍼 수명을 명시하고, Gymnasium과 학습기 고유 Vector API의 차이를 어댑터에서 처리한다.
- 독립 환경의 병렬 실행과 한 환경 안의 여러 에이전트를 구분한다.
  다중 에이전트는 ID별 행동/관측·공유/개별 보상·생성/제거와 동시/순차 행동 규칙을 정해 PettingZoo 어댑터를 추가한다.
- 통신/배치마다 버퍼 소유권을 정한다. 학습기가 보관한 관측이 다음 스텝의 재사용 버퍼 변경으로 덮어써지지 않게 한다.

근거: [Gymnasium Vector](https://gymnasium.farama.org/api/vector/),
[autoreset 계약](https://gymnasium.farama.org/api/vector/autoreset/),
[PettingZoo Parallel](https://pettingzoo.farama.org/api/parallel/).

### D. 센서·관측·물리 제어

- 첫 과제는 위치·속도·목표 방향·Raycast/접촉 같은 벡터 관측으로 완성한다.
  카메라 RGB·깊이·세그멘테이션·관절/접촉 센서는 별도 센서 모듈로 확장한다.
- 센서마다 좌표계·깊이 단위·색 공간·해상도·샘플 시각·step ID·유효성·지연을 전달한다.
  관측에 제공할 정보와 디버그용 내부 정답 상태를 구분해 의도치 않은 정보 누출을 방지한다.
- 영상은 RHI의 비동기 영역/전체 읽기·staging 버퍼·fence·링 버퍼를 검토한다.
  단일 픽셀 읽기를 모든 픽셀에 반복하거나 매 스텝 GPU 전체를 기다리는 방식을 기본 구현으로 삼지 않는다.
  지연된 프레임을 허용한다면 어떤 행동 이후의 관측인지 명시해 학습 데이터의 시간 관계를 보존한다.
- 힘/토크·관절 목표/PD 제어·관절 제한·접촉·질량/관성은 실제 과제에 맞춰 지원한다.
  로봇/휴머노이드 학습에서는 현재 제한된 Box 물리보다 안정적인 관절/접촉 해결이 먼저 필요하다.
  GPU 병렬 물리나 실제 로봇 전이는 첫 목표에 강제하지 않는다.

설계 참고: [Unity ML-Agents Agents](https://unity-technologies.github.io/ml-agents/Learning-Environment-Design-Agents/)의
관측·행동·보상 분리와 [Isaac Lab](https://isaac-sim.github.io/IsaacLab/main/source/api/lab/isaaclab.envs.html)의 환경/센서 구성을 비교한다.
API·배포 연동은 구현 시 해당 프로젝트의 현재 릴리스 문서로 다시 확인한다.

### E. 실험·랜덤화·평가

- 질량·마찰·시작 자세·목표·조명/텍스처·센서 노이즈·지연의 랜덤화를 과제 설정에 등록한다.
  분포·범위·상관·변경 시점·seed를 기록하고, 지원하지 않는 런타임 물리 변경을 조용히 적용한 것으로 처리하지 않는다.
- 난이도 단계·커리큘럼·성공률·보상 항목별 합·에피소드 길이·실패 원인·환경 steps/s를 기록한다.
  학습용 분포와 고정 평가 seed/조건을 분리하고 여러 실행의 결과 변동을 비교한다.
- 상태/행동 로그·선택적 snapshot·정책 버전·영상 기록으로 실패를 재현한다.
  매 스텝의 전체 씬 JSON·로그·영상 저장을 기본으로 삼지 않고 기록 주기·용량을 제한한다.
- 학습 계산 시간, 시뮬레이션, 관측 생성, 통신, GPU 읽기 비용을 따로 측정한다.
  높은 FPS나 steps/s만으로 물리 정확도·학습 성능·병렬 환경 확장성을 판단하지 않는다.

### F. 정책 추론·모션/리깅 최적화

- 학습은 우선 외부 Python 도구에서 수행하고, 엔진에는 학습된 정책의 추론을 선택 모듈로 넣는다.
  첫 후보는 [ONNX Runtime C++](https://onnxruntime.ai/docs/get-started/with-cpp.html)이며 채택·실행 공급자는 검증 후 확정한다.
- 관측 정규화·순서·단위·행동 스케일/클램프·순환 상태·모델 버전을 학습 때와 맞춘다.
  추론 세션과 버퍼를 재사용하고, CPU/GPU 전송·배치·스레드 수가 렌더링과 경쟁하는 비용을 측정한다.
  GPU를 선택하면 [I/O Binding](https://onnxruntime.ai/docs/performance/tune-performance/iobinding.html) 같은 복사 제어도 검토한다.
- 모션 학습은 기준 클립 추종·과제 수행·접촉/균형을 평가 대상으로 삼고,
  [DeepMimic 원 논문](https://arxiv.org/abs/1804.02717)을 물리 기반 모션 학습의 연구 출발점으로 둔다.
- 리깅/애니메이션 최적화는 뼈 수·웨이트·제약·모션 파라미터 등 변경할 대상을 먼저 좁힌다.
  포즈/실루엣·관절 오차·발 미끄러짐·관통·실행 비용과 웨이트 정규화·관절 제한 등 제약을 정의한다.
  단순 보간·IK·기존 최적화와 비교하고, 강화학습이 효과적인 대상일 때 적용한다.
- 결과는 지원하는 에셋/설정으로 저장·되돌리기·평가할 수 있어야 한다.
  학습 중간 상태를 그대로 제작 원본에 덮어쓰지 않는다.

### 강화학습의 단계별 완료 예제

1. 단일 수치 관측 환경에서 수동/무작위 행동→reset/step 검사→외부 학습→고정 평가를 실행한다.
2. 창/렌더러 없이 같은 과제를 실행하고 독립 프로세스 환경 수를 늘려 steps/s·메모리·상태 격리를 확인한다.
3. 시각 관측 또는 다중 에이전트 중 실제 필요한 하나를 추가하고 최종 관측·에피소드 경계·프레임 시각을 검증한다.
4. 단순 관절 과제 이후 모션 추종·리깅 최적화로 확장하고, 학습 결과를 Client의 선택적 추론 모듈로 재생한다.

## 16. 3D·2D V-Tuber 실행·추적·방송

### A. 3D 아바타 표준·표현

- glTF 2.0의 메시·스킨·애니메이션·morph target을 기반으로 VRM 1.0 임포트/실행을 목표로 한다.
  기존 `.gltf` 임포트나 뼈 데이터만으로 VRM 확장 지원이 완료됐다고 판단하지 않는다.
- humanoid 뼈 매핑·기준 포즈·좌표/단위·meta·표정·시선/1인칭·MToon·Spring Bone·노드 제약의 지원 범위를 명시한다.
  VRM 0.x는 필요할 때 별도 변환 경로로 추가하고 두 버전의 의미를 혼합하지 않는다.
- 눈깜빡임·입모양·감정·시선용 morph/재질 바인딩과 합성/배타 규칙을 구현한다.
  표정 가중치·기본 애니메이션·추적·IK·제약·보조 물리의 평가 순서와 적용 대상을 정의한다.
- 정점/법선 모프·스키닝·그림자·피킹·경계가 일관되게 갱신되는지 확인한다.
  툰 셰이더·윤곽선·투명도·양면·색 관리와 파라미터를 기존 머티리얼/RHI 규칙에 연결한다.

근거: [Khronos glTF 2.0](https://registry.khronos.org/glTF/specs/2.0/glTF-2.0.html),
[VRM 1.0](https://vrm.dev/en/vrm1/),
[VRM 규격·스키마](https://github.com/vrm-c/vrm-specification/tree/master/specification).
지원 확장은 항목별로 기록하며 알 수 없는 확장을 조용히 완전 지원으로 표시하지 않는다.

### B. 추적 입력·보정·장치 연결

- 웹캠·외부 모바일/트래커·VR 장치를 읽는 어댑터와 공통 얼굴/눈/손/몸 포즈 데이터를 분리한다.
- 데이터에 timestamp·source ID·좌표계·단위·신뢰도/유효성·중립 기준을 포함한다.
  미러링·화면 회전·장치 캘리브레이션·체형/팔 길이·추적 재획득과 입력 끊김의 동작을 정한다.
- 첫 연동은 [VMC Protocol](https://protocol.vmc.info/english.html) 같은 외부 추적 결과 수신으로 검증할 수 있다.
  VMC는 OSC over UDP 기반으로 뼈/표정 등을 전달하는 경로다. 게임 객체 복제와 같은 기능으로 취급하지 않는다.
- 자체 웹캠 추적은 [MediaPipe Face Landmarker](https://developers.google.com/edge/mediapipe/solutions/vision/face_landmarker)를 후보로 둔다.
  해당 출력의 얼굴 landmark·blendshape score·변환과 엔진 아바타의 표정/뼈 매핑을 별도로 처리한다.
  대상 플랫폼의 C++ 직접 통합 또는 별도 프로세스 연결을 비교하고, 문서의 다른 플랫폼 예제를 C++ API로 가정하지 않는다.
- 손·몸 추적과 선택적 XR 장치 연동을 단계적으로 확장한다.
  필터링·예측·보간은 떨림과 지연을 함께 측정하고, 제한된 큐에서 오래된 샘플·역순·유실을 처리한다.
  추적/추론 콜백에서 렌더링 객체를 직접 변경하지 않고 정한 프레임 경계에서 적용한다.

### C. 리타게팅·IK·보조 물리

- 추적/모션 소스의 휴머노이드 매핑·기준 자세·축을 아바타에 변환한다.
  두 뼈 IK·관절 제한·손/발 목표·시선부터 구현하고 필요에 따라 전신 IK·발 접촉 고정을 추가한다.
- 머리·눈·손·몸·기본 모션·수동 포즈/단축키의 우선순위·가중치·전환을 정한다.
  입력 추적이 없는 부위는 기본 포즈/애니메이션으로 복구하고 전신 IK를 첫 얼굴 추적의 선행 조건으로 만들지 않는다.
- 머리카락·옷·장식의 Spring Bone·충돌체를 고정 스텝과 안정적인 초기화로 처리한다.
  VRM의 보조 물리와 일반 천/소프트바디를 별도 기능으로 구분하고 필요할 때 확장한다.
- 실행 순서·반복 수·뼈/제약 수·충돌 검사·모프 업로드량을 측정하고 다중 아바타에도 독립 상태를 유지한다.

### D. 오디오 입력·립싱크·실시간 제어

- 마이크 장치·샘플률·채널·버퍼·시각·음소거·장치 변경을 지원한다.
  첫 입모양은 음량 기반으로 시작할 수 있으며 이후 음소/viseme 추론·재생 오디오 분석을 추가한다.
- 립싱크·얼굴 추적·감정 프리셋·자동 눈깜빡임이 같은 파라미터를 덮어쓸 때의 합성 규칙을 정한다.
- 2D 파라미터·3D 표정·소품·배경·카메라를 프리셋으로 제어하고, 사용자 단축키는 InputManager/액션 경로를 사용한다.
- 입력 영상·소리·추적 샘플의 타임스탬프와 출력 시각을 연결해 입모양/영상의 어긋남과 전체 지연을 측정한다.

### E. 2D 아바타 런타임

- 파츠별 텍스처/메시·그리기 순서·알파 합성·클리핑 마스크·변형·파라미터 보간과 모션/표정을 지원한다.
  단일 Sprite 교체나 Flipbook을 2D 리깅의 전체 기능으로 취급하지 않는다.
- 독자 2D 변형 에셋/평가기와 Live2D Cubism 형식 연동을 별도 목표로 둔다.
  Cubism 연동 후보는 [공식 Native SDK](https://docs.live2d.com/en/cubism-sdk-manual/cubism-sdk-for-native/)이며,
  엔진 RHI·렌더러 상태·마스크·지원 플랫폼/SDK 버전과 배포 조건을 도입 전에 확인한다.
- [실행용 데이터](https://docs.live2d.com/en/cubism-editor-manual/export-moc3-motion3-files/)와 제작 원본을 구분한다.
  `.model3.json`/`.moc3` 실행 지원이 `.cmo3` 편집이나 `.moc3` 생성기 제공까지 의미하지 않는다.
  자체 제작 도구의 저장·런타임 변환은 독자 포맷으로 먼저 완성하고 외부 포맷 입출력은 공식 지원 범위에서 검토한다.
- 얼굴·시선·입·물리 파라미터를 추적 공통 데이터에 매핑하고, 3D와 장치·프리셋·방송 출력 기반을 공유한다.
  모델별 메시 수·마스크 수·draw call·변형 CPU/GPU 비용과 숨긴 파츠의 생략 정책을 측정한다.

### F. 방송·영상 출력

- 초기에는 별도 Client 출력 창과 OBS 캡처로 검증하고, 투명 배경·해상도·FPS·색 공간·알파 규칙을 정의한다.
  게임/윈도 캡처의 실제 알파 지원과 녹화/방송 코덱의 알파 지원은 별도로 확인한다.
- 다음 단계로 Windows의 [Spout2](https://github.com/leadedge/Spout2) 공유 텍스처 연동을 검토한다.
  현재 DX12 자원과 해당 SDK의 지원 API·어댑터·동기화·수명 경계를 대조하며 임의 native handle 전달로 호환된다고 가정하지 않는다.
- 필요하면 OBS 플러그인·다른 영상 출력·가상 카메라를 선택 모듈로 추가한다.
  [OBS Virtual Camera](https://obsproject.com/kb/virtual-camera-guide)를 통한 웹캠 입력 앱 전달을 첫 후보로 두고,
  엔진 자체 가상 카메라 드라이버는 이후 별도 요구로 다룬다.
- 영상 기록은 프레임 timestamp·오디오 동기·인코딩 큐·드롭 정책을 정하고 렌더 루프를 블로킹하지 않는다.
  입력→추적→변형→렌더→캡처의 p95/p99 지연과 방송 중 장시간 메모리·자원·장치 재연결을 검증한다.

방송 참고: [OBS Game Capture](https://obsproject.com/kb/game-capture-source).
각 외부 SDK·모델은 사용 버전·지원 범위·재배포 조건을 기록한다. 첫 버전에 방송 플랫폼 로그인이나 자동 송출 API를 강제하지 않는다.

## 17. 모델·리깅·2D 아바타 제작 도구

사용자의 최종 범위는 외부 모델을 재생하는 것과 엔진 안에서 모델/리깅을 제작하는 것을 모두 포함한다.
제작 데이터는 Editor/도구 모듈이 소유하고 Engine에는 변환된 실행용 데이터와 평가 기능만 요구한다.
외부 DCC와의 임포트/익스포트를 유지하면서 자체 제작 기능을 점진적으로 확장한다.

### A. 3D 제작·스키닝·표정 편집

- 먼저 임포트한 메시의 정점/변/면 선택·기본 이동/회전/크기·피벗·법선/UV와 머티리얼 할당을 편집한다.
  원본 메시·공유 인스턴스·실행 중 GPU 버퍼를 구분하고 변경 시 필요한 캐시/BVH/경계만 갱신한다.
- 뼈 생성/삭제·계층·rest/bind pose·휴머노이드 매핑·소켓·제약을 편집하고 유효성 검사·Undo/Redo를 제공한다.
- 웨이트 페인트·정규화·미러·영향 뼈 수 제한·기초 자동 웨이트와 포즈 검사를 추가한다.
  뼈 순서 변경·삭제 시 정점 인덱스/모션 참조를 일관되게 재매핑한다.
- morph target 생성/수정·좌우 대칭·표정/viseme 바인딩·클립/커브 편집과 리타게팅 미리보기를 제공한다.
- 편집 원본·변환 옵션·런타임 결과·외부 원본 연결을 저장하고 재실행 후 제작 작업을 계속할 수 있게 한다.
  glTF/VRM 내보내기는 지원 규격·확장별 검증을 거쳐 추가한다.
- 이후 폴리곤 모델링 연산·UV 편집/전개·텍스처 페인트·조형·자동 리깅·리깅 최적화를 확장 목표로 둔다.
  외부 DCC 수준 전체를 첫 리깅 편집기의 완료 조건으로 삼지 않고 각 기능의 수치/형상 보존을 검증한다.

### B. 2D 파츠·메시·변형 제작

- 레이어별 이미지·파츠·피벗·메시 삼각분할·수동 정점 수정·텍스처 아틀라스·그리기 순서·마스크를 제작한다.
  초기에는 분리 이미지 임포트부터 시작하고 레이어 문서 임포트는 지원할 파일 규격을 정한 뒤 추가한다.
- 회전/워프 변형 계층·파라미터 범위·키 형태·복수 파라미터 보간·좌우 대칭과 영향 범위를 편집한다.
  [Cubism Deformer 문서](https://docs.live2d.com/en/cubism-editor-manual/deformer/)는 기능 비교 자료로 사용하며 독자 포맷 호환을 주장하지 않는다.
- 눈·입·호흡·물리·표정 프리셋·모션/커브와 추적 매핑을 미리보기하고 Undo/Redo·저장/복원을 제공한다.
- 편집 데이터와 압축/최적화된 실행용 데이터를 분리하고, 모델 수정 뒤 파라미터·마스크·추적 매핑이 유지되는지 검사한다.
- 완료 예제: 자체 도구에서 만든 간단한 2D 캐릭터를 별도 Client에서 얼굴/입 추적으로 구동하고 방송 캡처한다.
  3D도 자체 제작/수정한 간단한 리그·웨이트·표정을 저장·배치·추적해 같은 제작→실행 흐름을 확인한다.

### C. 아바타·학습 공통 제작 기반

- 커브·재사용 프리셋·명령 이력·안전한 문서 저장·리소스 의존성·임포트/변환·콘텐츠 썸네일을 기존 Editor 기능과 공유한다.
- 타임라인·리깅·학습 실험은 같은 실행 상태를 공유하지 않고, 읽기 전용 에셋과 명시적 결과 적용/되돌리기를 사용한다.
- 최적화는 사용자 선택 영역·허용 파라미터·목적 함수·제약과 비교 결과를 보여준 뒤 선택적으로 제작 데이터에 적용한다.
  모델 품질과 엔진 실행 비용을 함께 평가하고 학습 성공을 자동 품질 개선으로 표시하지 않는다.

## 18. 최종 결과물별 진행 단계와 검증

### 공통 기반을 먼저 좁게 완성

1. 제작/실행 데이터·참조·안전한 저장·엔티티/Scene 수명·성능 계측과 작은 Client 배포 예제를 완성한다.
2. 공통 UI 텍스트·입력 액션과 스키닝/모프·고정 스텝/초기화 중 각 결과물에 필요한 기반부터 연결한다.
3. 아래 결과물별 첫 완성 예제를 독립적으로 진행한다. 한 경로의 고급 기능 때문에 다른 경로를 전부 대기시키지 않는다.

### 게임 제작 경로

- 작은 2D/3D 씬→UI/입력→캐릭터/충돌→게임 저장→Client 배포를 완성한다.
- 그 게임의 요구에 따라 내비게이션/AI·파티클·트레일·시퀀스·타일맵·오디오를 추가한다.
- 런타임 로딩·씬 스트리밍·멀티플레이는 콘텐츠 규모/게임 규칙이 요구할 때 비용을 측정하며 확장한다.

### 강화학습 경로

- 벡터 관측의 단일 환경→외부 Gymnasium 학습→렌더러 없는 실행→프로세스별 병렬화→정책 Client 재생을 첫 결과물로 삼는다.
- 이후 영상 센서·다중 에이전트·도메인 랜덤화·관절 과제·모션/리깅 최적화로 확장한다.
- 처음부터 전신 휴머노이드·GPU 물리·로봇 실기 전이를 모두 요구하지 않는다.

### V-Tuber·제작 도구 경로

- 3D: 단순 리그/표정→VRM 지원 항목 검증→외부 추적 입력→얼굴/눈/립싱크→OBS 출력.
- 2D: 독자 변형 메시/파라미터의 작은 모델→추적 매핑→방송 출력. Cubism 연동은 별도 호환 경로로 검증한다.
- 제작: 임포트 데이터 검사/수정→3D 뼈/웨이트/모프 및 2D 파츠/변형 편집→안전한 저장→Client 변환/재생.
- 이후 전신/손 추적·고급 IK·보조 물리·제작 연산 확대·GPU 공유 출력과 장시간 방송을 검증한다.

## 19. 인게임 UI를 위한 런타임 설정 접근·적용

### 현재 방향과 보완 목표

- 현재 `ConfigManager`는 리플렉션 기반 설정 파일 읽기·쓰기를 담당하며 실행 중 설정 적용은 담당하지 않는다.
  `ProjectSettings`에는 시작 리소스/씬 등의 프로젝트 데이터가 있고 공통 사용자 그래픽 설정 타입은 확인되지 않았다.
- Editor의 `DrawDisplaySettingsWindow()`는 Application의 창 변경·UI 배율·목표 FPS 경로를 호출한다.
  Client는 별도 창/루프를 소유하고 VSync 초기값을 지정한다. 이 Editor UI 경로를 Client에 가져오지 않는다.
- 작은 타입별 설정 데이터와 공통 조회·검증·적용 경로를 추가해 Editor 패널·인게임 UI·스크립트/그래프가 재사용한다.
  임의 문자열 키로 모든 엔진 내부 값을 수정하는 범용 설정 시스템을 먼저 만들지 않는다.
- `GraphicsSettings` 같은 이름은 제안이다. 기존 Application·TimeManager·Renderer/RHI의 적용 기능을 연결하며,
  새 설정 소유자가 GPU 자원이나 플랫폼 창을 직접 소유하도록 재설계하지 않는다.

### 설정 데이터·공개 접근 범위

- 초기 대상은 출력 창 크기/모드·렌더 해상도 또는 배율·목표 FPS·VSync다.
  그림자·텍스처·후처리·안티앨리어싱·품질 프리셋은 실제 적용 경로가 생긴 항목부터 추가한다.
  항목을 선언하거나 UI를 표시한 것만으로 런타임 변경 지원을 표시하지 않는다.
- 화면 출력 크기·내부 렌더 해상도·UI 배율·게임 카메라 FOV는 적용 대상과 저장 범위를 구분한다.
  광원/머티리얼/씬의 제작값은 해당 에셋에 유지하며, 품질 설정은 명시적인 실행 정책이나 오버라이드로 적용한다.
- 공개 경로는 현재 실제 적용값·편집 초안·적용 대기값·기본값과 지원 범위를 구분한다.
  유효 범위·지원 해상도/창 모드·미지원 사유·즉시 적용/재생성/재시작 요구를 UI에서 조회할 수 있게 한다.
- 사용자 UI에는 허용한 옵션만 노출한다. 리플렉션 등록만으로 임의 필드 쓰기를 허용하지 않는다.
  그래프/스크립트는 설정 스냅샷 조회·검증된 적용 요청·결과 통지를 사용하고 내부 설정 객체의 변경 가능한 참조를 보관하지 않는다.
- 목표는 그래픽부터 완성하는 것이다. 오디오·언어·게임 UI 배율·입력 바인딩도 같은 사용 흐름을 따를 수 있지만,
  서로 다른 데이터와 적용 책임을 하나의 거대한 설정 관리자에 합치지 않는다.

### 적용·확정·취소와 안전한 실행 시점

1. UI를 열면 적용값을 초안에 복사한다. 초안을 편집하는 동안 외부 값으로 매 프레임 덮어쓰지 않는다.
2. 적용 요청을 값 범위·기능 지원·대상 유효성 기준으로 검사하고 변경 항목을 계산한다.
3. 요청을 소유 스레드와 안전한 프레임 경계에서 적용하고 실제 적용값·미지원/실패 항목을 반환한다.
4. 창 모드/해상도처럼 화면 확인이 필요한 변경은 미리보기 후 사용자 확정으로 유지한다.
   취소·확정 시간 초과·대상 소멸 시 마지막 사용 가능한 설정으로 되돌리고 되돌리기 실패도 보고한다.
5. 확정된 값만 저장한다. 실행 적용 성공과 저장 실패를 구분하고 저장 실패에서는 기존 파일을 보존한다.

- 창/모니터 변경은 Editor/Client 같은 호스트가, 프레임 제한은 실행 루프가, 렌더 품질·자원은 Renderer/RHI가 처리한다.
  공통 설정 경로는 필요한 호스트 적용 기능을 연결하며 Engine에 Editor 또는 ImGui 의존성을 추가하지 않는다.
- 창 크기 변경 요청과 OS 이벤트에 따른 실제 픽셀 크기 확정을 구분한다.
  RHI·렌더 타깃·뷰포트·입력 좌표를 기존 리사이즈 흐름에서 일관되게 갱신하고 중복 재생성을 피한다.
- GPU 자원 교체·swapchain 변경·사용 중 자원 해제는 실제 백엔드의 동기화 규칙을 따른다.
  슬라이더 입력마다 재생성/저장을 반복하지 않고 마지막 요청을 모으거나 명시적 적용을 사용한다.
- 여러 옵션의 부분 적용·실패 복구 정책을 정한다. 요청값을 무조건 현재 적용값으로 기록하지 않는다.
  적용 중 상태·완료 알림·실패 사유를 전달하고, UI를 닫아도 진행 중 요청의 수명을 안전하게 관리한다.
- 화면 확인 제한 시간은 게임 일시정지·타임 스케일과 독립적인 실제 시간으로 진행한다.
  사용자 확인을 기다리는 작업과 GPU 비동기 적용 완료를 같은 상태로 취급하지 않는다.

### 저장·부팅·여러 실행 대상

- 프로젝트 배포 기본값, 사용자 실행 설정, EditorPreferences/Workspace와 씬/에셋 제작값을 별도 데이터로 유지한다.
  Client 사용자 설정은 쓰기 가능한 앱/사용자 데이터 경로에 저장하고 Editor 개인 설정을 읽는 것을 전제로 삼지 않는다.
- 기본값→유효한 사용자 설정→명시적인 실행 시 임시 오버라이드의 우선순위를 정한다.
  임시 값과 하드웨어 제약으로 보정한 실제 값은 사용자의 확정 저장값과 구분한다.
- 일부 화면 설정은 창/RHI 생성 전에 읽어야 하므로 부팅 단계의 설정 로드·검증과 런타임 적용 단계를 구분한다.
  현재 Runtime의 리플렉션/RHI 초기화 순서를 확인해 로드 의존성을 연결한다.
- 스키마 버전·선택 필드·범위 검증·기본값 복원·안전한 그래픽 모드를 정한다.
  잘못된 파일이나 지원하지 않는 버전은 그대로 보존하고 복구 안내와 세션 fallback을 구분한다.
- Editor의 작업 창/뷰포트·PIE 출력·Client 출력은 적용 대상이 다르다. 한 프로세스의 실제 전역 설정은 그 제한을 표시한다.
  Editor FPS·PIE 그래픽·게임 사용자 저장값을 의도치 않게 함께 바꾸지 않는다.
- V-Tuber의 방송 출력 해상도/FPS와 조작 창 해상도, 강화학습의 센서 해상도·물리/정책 주기를 분리한다.
  그래픽 프리셋 변경이 학습 관측·시뮬레이션 시간이나 방송 출력 계약을 조용히 바꾸지 않게 한다.
- 헤드리스에서는 표시 장치 옵션을 미지원 또는 적용 불필요로 처리한다.
  패널을 열거나 설정을 조회한다는 이유로 GPU·창을 강제 초기화하지 않는다.

### 구현 단계와 완료 기준

1. 기존 FPS·창 크기 적용의 성공 여부·현재값 조회를 확인하고, 지원하는 소수 항목의 공통 경로를 만든다.
2. Editor 패널을 연결해 조회→초안→적용→결과→저장을 검증한다. 이후 인게임 UI를 같은 경로에 연결한다.
3. Client 부팅 기본값/사용자 설정 로드와 적용·확정·취소·안전 모드 복구를 완성한다.
4. VSync·품질 프리셋·스크립트/그래프 노출은 백엔드별 실제 지원 범위에 맞춰 확장한다.

- [ ] 같은 대상의 설정을 Editor·인게임 UI에서 바꿨을 때 조회값과 실제 화면이 일치한다.
- [ ] 저장 후 재실행·다른 모니터·DPI 변경·미지원 옵션·부분 실패·저장 실패를 처리한다.
- [ ] 화면 변경 확인 취소/시간 초과와 게임 일시정지 상태에서도 마지막 사용 가능한 설정으로 복귀한다.
- [ ] 반복 적용·창 크기 변경 이벤트·씬 교체·UI 종료 중 중복 작업·누수·오래된 완료 통지가 없다.
- [ ] 변경 없는 프레임에는 파일 읽기·설정 직렬화·GPU 자원 재생성을 반복하지 않는다.
- [ ] 옵션 이름·지원/실패 안내·확인/취소·프리셋 표시를 로캘 키로 제공하고 입력은 기존 공통 경로를 따른다.

이번 항목은 개발 계획이다. 공통 런타임 설정 API나 실제 인게임 그래픽 설정 UI를 구현한 것은 아니다.
