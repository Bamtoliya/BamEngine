## 1. 게임 개요

### 1.1 한 줄 소개 [확정 방향]

여러 문화권의 수호물에서 태어난 작은 토템들을 모아 군체를 구성하고, 물리적 적층과 협동, 공명 에너지 네트워크를 활용해 오염된 세계를 탐험·복원하며 자신만의 제작·자동화 공동체를 발전시키는 게임.

플레이어는 이름 없는 정령과 작은 토템을 중심으로 성장하는 군체를 이끈다. 마을에서 원정에 필요한 토템 개체, 적층 구조, 역할과 보급품을 편성하고 넓은 지역으로 출정한다. 전투는 자동 공격과 군체 지휘, 설치형 구조물, 물리 상호작용 및 공명에 집중한다. 획득한 재료와 동료를 마을로 가져와 생산망을 개선하고, 복원한 세계를 영구적으로 연결해 새로운 지역을 해금한다.

### 1.2 게임의 핵심 재미

- **문화적 정체성:** 각 문화의 상징물은 외형뿐 아니라 고유한 기능과 행동, 공간 배치 특성을 가진다.
- **물리적 협동:** 살아 있는 토템이 서로 쌓이고 균형을 잡으며 물체를 함께 운반한다.
- **조합과 공명:** 고유 개체를 유지한 채 공통된 능력·물리·에너지 규칙으로 새로운 연계를 만든다.
- **위험과 보상:** 원정에서 언제 귀환할지 선택하고, 더 오래 깊게 탐험할수록 커지는 보상과 위협을 관리한다.
- **살아 있는 공동체:** 탐험에 쓰는 토템이 마을에 돌아와 직접 채집·운반·제작·방어 활동을 수행한다.
- **장기적인 창작:** 마을 배치와 물류, 에너지망 및 출정 조합을 자유롭게 설계하고 실험한다.

### 1.3 분위기와 표현 [확정]

귀엽고 유쾌하면서 신비로운 로우폴리 3D. 실패나 파손은 잔혹한 묘사 대신 흔들림, 균열, 분리 및 수리로 표현한다. 위협과 긴장감은 유지하되 토템 공동체에 대한 애착을 해치지 않는다.

## 2. 세계관과 문화권

### 2.1 세계관 골격

[확정] 문화권별로 나뉘어 단절된 세계가 존재한다. 오염되거나 황폐해진 지역을 복원함에 따라 서로 연결되고 토템 공동체가 성장한다.

[제안] 이름 없는 정령이 작은 토템의 몸에서 깨어난다. 기억을 잃은 정령은 잠든 수호자들을 만나고, 각 지역의 잃어버린 연결을 되살린다. 중앙 마을은 여러 문화가 만나되 각자의 정체성을 잃지 않는 공간이다. 오염의 원인과 정령의 기원, 이야기의 결말은 추후 결정한다.

### 2.2 문화권과 기능 후보

여기서 ‘토템’은 게임 내 편의상 수호상·상징물·의례 건축물·거석 구조물을 포함하는 포괄적 명칭이다. 실제 문화에서 모두 토템으로 분류되는 것은 아니다. 아래 능력은 역사적 사실이 아니라 **창작 기능 후보**이며 실제 전통의 맥락은 콘텐츠 제작 전에 별도로 검증한다.

| 문화권 / 모티브 | 조형적 특징 | 게임적 기능 후보 |
|---|---|---|
| 한국 — 장승 | 세로 기둥, 조각된 얼굴, 목재·석재 | 수호, 결계, 길목 방어, 충돌 억제 |
| 한국 — 솟대 | 높은 기둥과 새의 실루엣 | 공명 중계, 감지, 높은 위치를 통한 범위 확보 |
| 북아메리카 북서 해안 원주민 — 토템폴 | 수직 배열과 조각된 상징 | 적층 지원, 능력 전달, 안정성 보조 |
| 일본 — 도리이 | 문 형태의 구조, 뚜렷한 실루엣 | 이동 통로, 지역 연결, 에너지 전송 |
| 라파누이 — 모아이 | 석조 인물상의 큰 질량과 실루엣 | 협동 운반, 안정적인 하단 지지, 중량 물리 행동 |
| 영국 신석기 거석 — 스톤헨지 모티브 | 원형 배열, 거대한 석재 | 집단 공명, 에너지 정제·저장, 영역 효과 |
| 안데스 — 티와나쿠 석상 및 석문 모티브 | 석조 인물상과 기하학적 문양 | 조건형 에너지 변환, 유적 활성화 |

문화별 기능을 하나의 정형화된 민족적 성격으로 고정하지 않는다. 북서 해안 토템폴의 수직 조립은 게임적 각색이며, 실제 기둥을 자유롭게 합체하는 전통으로 소개하지 않는다. 신성한 문양·가문 상징·종교적 요소는 권리 및 문화적 맥락을 검토하고 필요하면 해당 공동체의 자문을 구한다. 스톤헨지의 정확한 건립 목적도 단정하지 않는다. 현재 문서에는 신규 문화사 자료 검증이 포함되어 있지 않다.

## 3. 전체 플레이 구조

### 3.1 이중 성장 루프 [확정]

```text
[영구 허브 마을]
    채집 → 운반 → 가공 → 제작·수리·성장
    생산 시설·물류·에너지망 설계
    토템 선택 + 적층 + 편성 프리셋 구성
                   ↓ 출정
[일정 크기의 넓은 로그라이트 탐험 지역]
    자유 탐험 / 자원 회수 / 전투 / 동료 각성 / 유적 복원
    시간이 지날수록 위협 증가, 깊은 탐험일수록 보상 증가
                   ↓ 언제든 귀환 선택 또는 실패
[정산 및 마을 복귀]
    재료·동료·복원 성과 반영, 파손 토템 수리
    영구 성장 + 다음 지역 연결 → 새로운 편성 → 재출정
```

### 3.2 탐험 루프의 원칙

- 방 단위의 순차 진행보다 일정 범위 안에서 자유롭게 탐험하는 방식.
- 자원, 유적, 적, 잠든 토템, 위험 구역의 위치와 우회로를 읽고 이동한다.
- 적의 성장과 자원 운반 부담 사이에서 원정 연장 또는 귀환을 결정한다.
- 지역 복원과 연결은 영구적 진척이며, 이후에도 해당 지역을 다시 방문할 수 있다.
- [제안] 초기에는 손으로 만든 지형과 랜덤 배치 조합을 활용한다. 완전 절차 생성은 핵심 재미 검증 이후 진행한다.

## 4. 플레이어 및 카메라

### 4.1 플레이어 정체성 [확정 방향]

작은 토템 직접 조작, 이름 없는 정령, 토템 군체라는 요소를 함께 채택한다.

[제안] 정령이 최초의 작은 토템에 깃들어 움직이고, 군체의 나머지 개체에 명령한다. 다른 토템으로 조종 대상을 전환하는 빙의 기능은 자연스러운 확장 후보이나 전환 비용·범위·쿨다운과 필수 여부는 미정이다. 직접 공격 연타보다는 위치 선정, 행동 지정, 군체 운용을 우선한다.

### 4.2 카메라 및 입력 [확정 + 제안]

3D 쿼터뷰, WASD 직접 이동 + 마우스 군체 명령. 카메라 기준 지면 XZ 평면 이동, 화면과 월드 좌표 변환, UI 입력 우선 처리 필요. 원근/직교 투영 방식 및 회전 범위는 미정이다.

| 입력 (예시) | 기능 |
|---|---|
| WASD | 현재 조종 토템 직접 이동 |
| 좌클릭 / 드래그 | 개체 선택 / 범위 다중 선택 |
| Shift + 선택 | 선택 추가·제거 |
| 우클릭 | 위치 이동 / 대상 공격 / 운반 / 상호작용 등 문맥 명령 |
| 숫자키 | 군체 그룹 선택 또는 프리셋 호출 |
| 지정 단축키 | 집결, 대기, 적층, 분리, 배치 |
| 휠 | 카메라 확대·축소 |
| 귀환 버튼 | 귀환 요청 및 정산 전 확인 |

키 배치 및 직접 공격 기능은 미정. 선택과 명령이 이동 조작을 방해하지 않게 하고, 카메라 가림 시 실루엣 또는 투명 처리로 조종 상태를 읽을 수 있어야 한다.

### 4.3 군체 규모 [확정 방향]

초반 소수에서 지속적으로 확장된다. [제안] 마을 전체 인구와 원정에 참여하는 개체의 예산을 분리한다. 원정 제한은 군체 수, 적층 슬롯, 지휘력/공명 용량 또는 총 비용으로 설계할 수 있으나 방식과 상한은 미정이다. 개체 증가에 따른 관리 부담은 그룹 명령과 역할 기반 자동 행동으로 완화한다.

## 5. 토템 개체와 생명주기

### 5.1 유형

- [확정] 생명형: 이동·공격·채집·운반·협동 수행.
- [확정] 고정형: 결계·공명·생산망·공간 연결 등 설치된 기능 수행.
- [제안] 각성형: 조건 충족 시 고정/생명 상태를 전환하는 일부 토템. 모든 고정형에 이동 기능을 강제하지 않는다.

### 5.2 획득 및 성장 [확정]

1. 폐허에서 잠든 토템 깨우기.
2. 재료를 수집하고 직접 조각·제작하기.
3. 전투에서 승리해 동료로 영입하기.
4. 특정 지역을 복원해 해당 지역 토템 합류시키기.
5. 기존 토템을 성장시키거나 새로운 형태로 각성시키기.

동일한 장승도 서로 다른 개체로 취급한다. 이름, 고유 ID, 재질, 크기, 문양, 수리 상태, 성장 이력 등을 독립 저장한다. 성격·친밀도·개별 AI까지 필요한지는 미정이다. [제안] 개체별 기본 능력은 종족/원형 정의를 공유하고, 실제 스탯과 성장·외형·소속만 독립 인스턴스로 저장해 콘텐츠 제작량을 제한한다.

### 5.3 파손과 복원

정상 → 손상 → 파손/비활성 → 마을 수리 → 정상. [제안] 전투 중 파손된 토템은 행동을 중단하며, 귀환·실패 정산 시 수리 대기 명단에 기록한다. 수리 재료와 흔적은 개체의 이야기와 경제적 비용을 형성한다. 영구 사망은 채택하지 않는다.

## 6. 출정 편성 및 적층 커스터마이징

### 6.1 원정 덱(Expedition Loadout) [확정 방향]

마을에서 원하는 토템 개체와 조합, 적층 구조를 구성한 뒤 출정한다. **여기서 덱은 카드 드로우 전투가 아니라 군체 편성/로드아웃의 개념**으로 해석한다. 카드 게임 도입 여부는 별도로 결정한다.

[제안] 편성 화면은 다음을 지원한다.

| 항목 | 편성 내용 |
|---|---|
| 선발 개체 | 보유 토템 중 원정 참가자 선택 |
| 지휘 토템 | 직접 조종할 개체 선택 |
| 분대 | 전투·운반·공명·방어 등의 그룹 배정 |
| 적층 프리셋 | 하단부터 상단까지 개체 및 접점 순서 설정 |
| 설치형 | 원정에 가져갈 설치물과 배치 가능 수량 |
| 연결 구성 | 에너지 공급원·중계·소비 역할 및 우선순위 |
| 보급 | 수리용 재료 또는 소모품 (도입 여부 미정) |
| 검증 | 중복 배치, 파손 여부, 질량·높이·비용, 빈 역할 경고 |

개체가 물리적으로 쌓여도 하나의 새 종족으로 합쳐지지는 않는다. 모든 조합에 전용 스킬과 모델을 만드는 대신 개별 능력과 공통 접점 규칙을 사용한다. 같은 개체를 서로 다른 원정 슬롯에 중복 등록하지 않는다. 프리셋은 개체 ID를 참조하며 사용할 수 없는 개체를 표시한다.

### 6.2 편성 예시 [제안]

| 예시 | 구성 및 전략 | 장단점 |
|---|---|---|
| 수호 원정대 | 지휘 토템, 장승 2, 솟대 1, 운반 토템 3 | 결계와 자원 회수에 강점, 화력 부족 가능 |
| 높은 공명탑 | 모아이 하단 + 장승/토템폴 중단 + 솟대 상단 | 넓은 중계 범위, 높이·회전 안정성 부담 |
| 물류 원정대 | 소형 운반 토템 다수 + 중량 지원 모아이 | 무거운 유물 회수, 전투 인원 감소 |
| 거점 원정대 | 장승 설치물 + 솟대 중계 + 소수 생명형 | 임시 안전 지대, 설치 및 회수 비용 |

이 예시들은 확정된 토템 능력이나 수량 제한이 아니다.

### 6.3 적층과 균형 [확정 + 제안]

각 토템은 독립 개체로서 질량·크기·중심점·연결 접점·허용 하중을 가진다. 적층 순서에 따라 안정성, 높이, 능력 범위, 이동 저항이 변한다.

[제안] 초기에는 접점에 스냅하고 하나의 이동 루트/복합 충돌 형상을 쓰며, 전복·파손 조건이 충족될 때 분리된 강체로 전환하는 하이브리드 방식을 사용한다. 완전한 강체 적층을 기본으로 강제하지 않는다. 지면 지지 영역으로 투영한 질량중심, 경사, 가속도, 하중으로 안정성을 판정하고, 안전/주의/붕괴 위험을 표시한다. 정적인 무게중심 판정은 동적 안정성을 보장하지 않으므로 별도 물리 테스트가 필요하다.

- 탐험 중 적층·분리 허용 범위와 전투 중 변경 비용은 미정.
- 높이·중량에 이득과 위험이 함께 있어 하나의 적층 순서가 모든 상황의 정답이 되지 않도록 한다.
- 붕괴 시 각 개체의 ID와 상태를 유지하며 중복 생성·소실을 방지한다.

## 7. 군체 AI와 협동 운반

### 7.1 지휘 및 자동 행동

[제안] 명령을 개체 또는 분대에 전달하고 각 개체가 수행 가능한 행동을 선택한다. 기본 상태: Follow / Move / Attack / Guard / Carry / Stack / Work / Return / Disabled. 플레이어의 명시적 명령은 일반 자동 행동보다 우선하고 안전상 취소 조건과 파손은 최상위로 처리한다.

추종 중 분대 슬롯을 활용하고, 좁은 통로에서는 대형을 해체하거나 줄을 서도록 한다. 작업 중 대상이 사라지거나 길이 차단되면 작업을 취소·재계획한다. 규모가 커져도 각 개체를 직접 클릭할 필요가 없도록 그룹 및 역할 명령을 제공한다.

### 7.2 협동 운반 [확정 방향]

여러 토템이 물체의 무게와 운반 접점에 따라 힘을 합친다. 탐험에서 유물·재료 회수, 전투에서 장애물 이동, 마을에서 생산 물류에 같은 시스템을 활용한다.

[제안] 물체별 운반 슬롯 예약 → 필요 운반력 충족 → 함께 이동 → 목적지 인계의 공통 파이프라인. 힘이 부족하거나 일원이 파손되면 속도가 줄거나 안전하게 내려놓는다. 초기에는 물체 하나를 이동 주체로 두고 운반자는 상대 접점에 따라간다. 개별 강체가 각자 힘을 가하는 완전 물리 운반은 후속 실험으로 분리한다.

## 8. 공명 및 능력 연계

### 8.1 공통 규칙 [확정 방향]

문화와 개체의 고유 능력을 유지하되 모든 쌍별 조합을 하드코딩하지 않는다. 연결과 공명이 탐험, 전투, 자동화에 공통 활용된다.

[제안] 에너지 공급(Source), 중계(Relay), 저장(Storage), 변환(Converter), 소비(Consumer) 등 역할을 데이터로 정의하고 거리·방향·포트·장애물·용량에 따라 연결한다. 능력에는 발동 조건, 범위, 쿨다운, 에너지 요구량, 대상 필터, 출력 효과를 둔다.

```text
에너지원 → 솟대 중계 → 장승 결계
                     ↘ 거석 정제기 → 제작 공방
```

이 예시에서 솟대는 장승을 위한 전용 조합을 갖는 것이 아니라, 규칙에 맞는 소비자에게 에너지를 전달한다. 장승은 공급량에 따라 결계의 기능을 조정한다. 직접 연결과 적층 접점 모두 동일한 포트 규칙을 공유할 수 있다.

### 8.2 네트워크 설계 제안

- 연결 그래프: 안정적인 노드/포트 ID, 방향, 거리, 용량, 손실률, 활성 조건.
- 첫 버전: 단일 에너지 타입 및 공급량, 우선순위 기반 배분, 무한 재순환 금지.
- 변경 시 인접 그래프 갱신, 고정 논리 틱에서 공급·소비 계산. 화면 연결선은 결과를 읽어 보간한다.
- 순환 연결은 초기에는 차단하거나 별도 저장·보존 규칙으로 처리. 증폭이 무한 에너지를 만드는 오류를 막는다.
- 공명이 끊긴 이유(거리, 차폐, 공급 부족, 파손)를 UI로 보여준다.
- 충돌·연계 효과 이벤트에는 중복 방지 및 연쇄 깊이 제한을 둔다.

## 9. 전투

### 9.1 채택 방식 [확정]

| 방식 | 역할 |
|---|---|
| 자동 전투 | 각 토템이 조건에 따라 자동 공격 및 방어 |
| 설치형 전투 | 고정형 토템 배치, 결계 및 전장 구성 |
| 물리 전투 | 충돌, 무게, 적층 붕괴 및 물체 이용 |
| 공명 전투 | 연결을 통해 능력 발동·증폭·연쇄 효과 |
| 군체 전투 | 분대 이동·목표 지정·역할 배치·집결 명령 |

[제안] 다섯 전투를 별도의 모드로 나누지 않고 하나의 전장에 결합한다. 토템 자동 공격은 전투 기본 처리, 군체 명령과 설치·공명·물리가 플레이어의 주요 전략 개입 수단이다. 직접 공격 여부는 미정이다.

### 9.2 전투 사례 [제안]

유적 복원 장치를 공격하는 오염된 적이 접근한다. 장승을 설치해 안전 구역을 만들고 솟대로 에너지를 중계한다. 일부 동료는 자동 전투를 수행하는 동안 운반 분대는 무거운 석상을 이동시켜 진입로를 막고 복원 분대는 유물을 회수한다. 전투 결과는 딜량 외에도 방어·운반·복원 목표 달성으로 평가된다.

적과 보스의 종류, 웨이브/스폰 규칙, 공격 사거리, 전투 난이도 등은 미정. 초기에는 오염된 정령/가상 생물 등 실제 문화 자체를 적대 세력으로 묘사하지 않는 방향을 제안한다.

## 10. 로그라이트 원정, 귀환, 계승

### 10.1 지역 구조 [확정]

일정 크기의 넓은 지역을 자유롭게 탐험하고 목표를 달성한다. 언제든 귀환할 수 있으며 깊이 들어갈수록 보상이 증가하고 시간이 지날수록 적이 강해진다.

[제안] 지형을 위험도/진행 깊이 구간으로 구분하되 강제 순서 없이 탐험한다. 위험도는 원정 경과 시간과 현재 구역의 기본 위험에 따라 증가한다. 보상은 위험 구간과 유적·운반 난이도에 의해 결정하고 단순히 대기하는 것만으로 보상이 늘어나지는 않게 한다. 언제든 귀환 요청이 가능하도록 하고, 전투 중 즉시 귀환인지 짧은 준비 시간 또는 안전 조건을 적용할지는 미정이다.

### 10.2 결과와 실패 처리 [확정]

| 요소 | 정상 귀환 (제안) | 실패 (확정) |
|---|---|---|
| 동료 | 상태를 유지해 귀환 | 파손 후 수리 |
| 원정 재료 | 회수한 재료 보존 | 일부 보존 |
| 원정 강화 | 일부 영구 성장 반영 | 일부 계승 |
| 지역 복원 | 영구 유지 | 영구 유지 |
| 마을 발전 | 영구 유지 | 영구 유지 |

보존 비율, 수리 비용, 영입 직후 실패 시 새 동료의 처리 및 성공 귀환 시 강화 계승 비율은 미정이다. [제안] 복원 완료는 즉시 영구 플래그에 기록하고, 원정에서 획득한 자산은 정산 트랜잭션으로 한 번만 반영한다. 동일 원정 ID의 중복 정산, 저장 도중 종료, 실패 후 재접속에 따른 복제 버그를 방지한다.

## 11. 마을 제작과 자동화

### 11.1 방향 [확정]

제작 및 자동화형 마을. 플레이어가 생산 시설의 배치, 운반 경로, 재료 공급, 에너지 연결을 직접 설계한다. 단순히 메뉴에서 수치를 올리는 마을이 아닌 토템이 움직이며 일하는 공동체이다.

### 11.2 생산 흐름 [제안]

```text
목재·석재 채집 → 운반 → 창고 → 가공 공방 → 조각·제작·수리 공방
                                       ↑
                         에너지원 → 공명 중계망
                                       ↓
                  새 토템 / 원정 보급 / 시설 / 마을 확장
```

| 시스템 | 요구 기능 |
|---|---|
| 시설 배치 | 설치 미리보기, 충돌·지면·통로 검사, 회전, 이동·철거 |
| 재료 저장 | 수량, 용량, 입출력 예약, 부족·포화 상태 |
| 운반 경로 | 출발지·목적지, 경유점, 운반 우선순위, 대체 경로 |
| 작업 할당 | 개체/분대 및 시설 역할, 작업 우선순위, 자동 재할당 |
| 제작 | 레시피, 입력 소비, 작업 시간, 출력 보관, 취소/반환 |
| 에너지망 | 연결 포트, 공급/부족, 소비 우선순위, 연결 단절 |
| 수리 | 파손 개체와 필요 재료, 수리 시간, 복원 이력 |
| 방어 | 고정형 토템과 공명을 활용한 영역 보호 |

[제안] 자원은 초기 목재·석재·정령 결정 3종으로 시작하고 확장한다. 토템의 고유 능력이 마을 작업에도 영향을 준다. 탐험에 데려간 개체는 마을의 작업 가용 인력에서 제외한다. 오프라인 생산, 원정 중 마을 시간 진행, 본격적인 컨베이어 도입 및 자동화의 경제 밸런스는 미정이다. 첫 프로토타입에서는 마을을 벗어나면 생산을 멈추는 방식도 검토한다.

## 12. 영구 세계 성장

지역별 복원 상태 및 연결을 유지하고 신규 토템·제작법·시설·자원을 해금한다. 정해진 목표 이외에도 자유롭게 탐험하고 실험할 수 있으며, 공동체 구축과 수집·성장이 장기 목표가 된다. [제안] 지역의 고정된 복원 포인트는 안정적인 ID로 관리하고, 재방문 시 시드가 달라져도 복원 결과를 재적용한다. 탐험 시드와 영구 복원 기록을 분리한다.

## 13. 아트, 애니메이션, UX

### 13.1 로우폴리 스타일 [확정]

3D 로우폴리 조형을 사용한다. [제안] 목각과 석재의 질감은 복잡한 사실적 디테일보다 면의 방향, 색 분리, 조각 문양, 실루엣으로 표현한다. 색상과 재질은 문화권별로 구별되되 공통 조명과 명도 규칙을 따른다.

- 이동: 통통 튀기, 좌우 흔들기, 기울기, 돌의 묵직한 보행 등 개체별 특성.
- 협동: 운반 시 몸을 낮추거나 힘을 주는 동작, 적층 시 균형 보정 및 흔들림.
- 전투: 단순하고 읽기 쉬운 타격, 결계와 에너지 방향 표시, 파손 효과.
- 복원: 오염의 걷힘, 문양 점등, 자연·조명의 변화, 신비로운 음향.
- 로우폴리는 반드시 Toon/NPR 셰이더를 필요로 하지 않는다. 현재 PBR/기본 셰이더로 먼저 아트 스타일을 검증한다.

### 13.2 UI 및 가독성 [제안]

원정 편성 드래그앤드롭과 3D 적층 미리보기, 군체 선택 및 명령 표시, 상태/체력/파손, 미니맵과 위험도, 귀환 정산, 생산량·재료·공명망 오버레이, 개체 도감과 수리 기록. 군체 규모가 커지면 모든 이름표 표시 대신 선택 대상 및 이상 상태 위주로 보여준다. 색만으로 상태를 구분하지 않고 아이콘/선 모양/텍스트를 병행한다.

### 14.3 이번 조사에서 특별히 발견한 기술 위험

1. **NavAgent와 물리 권한 충돌:** `NavigationSystem.cpp`는 경로를 추적하면서 transform/velocity 기반 이동을 처리한다. 적층체·운반체·캐릭터 컨트롤러와 같은 엔티티를 동시에 구동하지 않도록 이동 주체를 명확히 분리해야 한다. 전체 구현의 호출 순서와 동기화는 후속 조사 필요.
2. **AI 감지 스케일:** 감지자마다 Transform 후보 전체를 순회하는 코드가 확인된다. 대군체 + 적 + 시설 환경에서 병목 후보. 공간 해시, 레이어 필터, 거리 제곱 비교, LOS 예산 및 업데이트 분산을 우선 검증한다.
3. **조인트 한계:** Distance Joint만으로 수직 접점 고정과 각도 유지가 보장되지 않는다. 물리 해석 의존적 적층보다 스냅/복합체 방식으로 먼저 플레이를 검증한다. 런타임 강체 전환 및 참조 직렬화 필요.
4. **세이브 데이터 범위:** `SaveGameData`는 메타데이터, 플레이어 위치·회전·체력, 정수/실수/불리언/문자열 플래그 맵을 보유한다. 군체 수십~수백 개체와 생산망을 무리하게 플래그로 인코딩하지 않고 확장 가능한 구조화 스키마를 설계한다.
5. **전투 확장:** 기존 `GameplayCombatSystem.cpp`는 Hitbox 기반 질의와 피해 적용을 담당한다. 자동 공격 정책, 공격 예약, 공명 효과 및 팀 전체의 지휘 시스템을 이미 지원한다고 해석해서는 안 된다.
6. **물리 문서의 최신성:** 기존 슬라임 Gap 문서는 CCD와 비트리거 충돌 이벤트를 미구현으로 기록했지만, 이번 커밋의 `RigidBodyComponent.h`와 `PhysicsSystem.h`에는 관련 설정/이벤트 API가 보인다. 실제 구현과 테스트를 확인하기 전까지 완성으로 판단하지 않으며 기존 문서의 부재 판정도 그대로 복사하지 않는다.

## 15. 신규 및 확장 기술의 권장 설계

### 15.1 엔진 vs 게임 모듈 책임 경계

| 계층 | 권장 책임 |
|---|---|
| BamEngine 코어 | 이동·공간 질의·경로·국소 회피·스케줄링, 물리 접점/제약 및 직렬화, 범용 이벤트·저장·UI·렌더링·디버그 |
| Editor | 배치 및 접점 편집, Nav/군체/물리/그래프 디버그, 데이터 에셋 검증, 프로파일링, 프로젝트 전환 및 PIE |
| 토템 게임 모듈 | 토템 정의와 개체 생명주기, 원정 편성, 적층 규칙, 작업·운반 정책, 공명 경제, 전투 정책, 마을 생산, 원정 정산, 지역 복원 |
| 게임 콘텐츠 | 문화 모티브 모델·애니메이션·음향, 레시피, 지역 지형·유적, 적 및 보상, UI 프리팹 |

처음부터 범용 자동화 엔진 전체를 만들지 않는다. 토템 게임에서 실제 사용해 안정된 공통 기능만 엔진 코어에 승격한다. 기존 `Projects/GameModule` 또는 독립 게임 프로젝트를 이용하되 구체 모듈명과 디렉터리 구조는 프로젝트 전환 계약을 확인한 후 정한다.

### 15.2 데이터 모델 예시 (새 게임 코드 제안, 기존 심볼 아님)

```cpp
// 정의 에셋: 많은 개체가 공유하는 콘텐츠 데이터
struct TotemDefinition {
    DefinitionId id;
    CultureId culture;
    PrefabId prefab;
    float baseMass;
    float baseHealth;
    std::vector<AbilityId> abilities;
    std::vector<SocketDefinition> stackSockets;
    std::vector<PortDefinition> resonancePorts;
};
// 영구 상태: 씬 런타임 entt::entity와 별개
struct TotemInstanceData {
    TotemId id;
    DefinitionId definition;
    std::string name;
    float condition;
    uint32_t level;
    MaterialId material;
    AppearanceSeed appearance;
};
struct ExpeditionLoadout {
    TotemId leader;
    std::vector<TotemId> members;
    std::vector<SquadDefinition> squads;
    std::vector<StackPreset> stacks;
    std::vector<PlaceableEntry> deployables;
};
```

실제 ID 타입 및 컨테이너는 BamEngine의 기존 reflection/archive/asset ID 계약과 호환되는 형태로 선택한다. 영구 ID에서 런타임 엔티티로 매핑하고 씬 재생성 시 참조를 해결한다. `entt::entity`를 저장 파일의 안정 ID로 쓰지 않는다.

### 15.3 시뮬레이션 구성

[제안] 입력 수집 → 선택/명령 큐 → AI/작업 스케줄 → 경로·이동 의도 → 적층/운반 주체 갱신 → 고정 물리 틱 → 충돌 결과/피해/파손 이벤트 → 공명·생산/원정 논리 틱 → 표현 및 UI 갱신. 이는 목표 의존 순서이며 기존 `ISystem` 실행 단계 및 물리 업데이트 순서에 맞게 조정한다.

- 개체별 행동을 매 프레임 전부 검색하지 않도록 이벤트/저주기 상태 평가 활용.
- 논리 틱과 렌더링을 분리하고 이동/애니메이션은 보간한다.
- 각 개체의 이동 책임은 직접 조작 / NavAgent / 적층 루트 / 운반 루트 / 강체 중 하나로 명시한다.
- 저장/씬 전환 시 명령 큐, 작업 예약, 임시 제약, 그래프 노드 참조를 안전하게 해제한다.

### 15.4 우선순위별 요구사항 및 완료 기준

P0 = 핵심 재미를 검증하기 위한 필수, P1 = 플레이 가능한 세로 슬라이스, P2 = 확장 및 품질. 상태는 14장의 근거를 따른다.

| ID | 우선순위 / 기술 | 최소 완료 기준 |
|---|---|---|
| T01 | P0 쿼터뷰 및 명령 입력 | WASD/클릭/드래그/우클릭을 동시에 사용하고 UI 위 클릭이 월드 명령을 발행하지 않음 |
| T02 | P0 군체 이동 및 회피 | 10~30개가 목표 도달, 좁은 길에서 재배치, 막힘 복구; 이동 책임 중복 없음 |
| T03 | P0 안정 ID 및 편성 | 동일 종류 개체 두 개를 구별, 적층 프리셋 저장/재호출, 중복 및 파손 참가 제한 |
| T04 | P0 적층 | 접점으로 2~4단 적층, 안정성 표시, 이동 중 제어, 충격 분리 및 개체 보존 |

### 15.5 추가 조사와 선택 기준

- NavMesh: 현재 자체 빌더의 동적 장애물/다양한 크기 에이전트/경로 동시 처리 검증. 기존 `INavMeshBuilder` 확장 지점으로 Recast/Detour 계열 도입 여부를 실제 병목에 따라 판단. 외부 라이브러리 버전 및 라이선스는 별도 검증.
- 물리: Distance Joint 실제 솔버, 접촉점/충격량 이벤트, CCD 동작, 마찰·휴면·관성, 복합 충돌, FixedUpdate 타임스텝을 검증. 현재 엔진 물리를 우선 활용하고 필요시 PhysX 등 외부 솔버를 비교하며 선제 전면 교체는 하지 않는다.
- 그래프: 공명 공급량 배분에서 순환, 지연, 다중 소비, 장애물 검사의 비용과 읽기 쉬운 UX 검토.
- 생성: 시드와 저장 스키마 버전, 지형·Nav 연결성, 중복 생성, 영구 복원 지점 ID의 호환성 연구.
- 저장: 원자적 파일 교체의 플랫폼별 실패 복구, 개체/시설/작업의 교차 참조, 저장 중 종료 및 스키마 마이그레이션.
- 에디터: 멀티 프로젝트 루트 전환, 프로젝트별 Asset/Scene/Save 경로, 런타임 prefab 생성, 게임 모듈 핫리로드 및 PIE 정리 계약 검증.
- 성능: 기존 Metrics 패널과 엔진 계측을 활용하되 릴리스 빌드/대표 장면에서 CPU, GPU, 물리, 경로 요청, 감지 및 생산 틱을 측정한다.

## 16. MVP 및 단계별 개발 순서

게임 전체의 시스템 수가 많으므로 먼저 **편성한 군체를 이끌고 적층·운반·공명으로 원정을 해결한 뒤 마을 제작에 성과를 반영하는 한 사이클**을 검증한다. 다음 수량은 일정 약속이 아니라 초기 테스트 범위이다.

| 단계 | 구현 범위 | 통과 조건 |
|---|---|---|
| M0 기반 검증 | 독립 프로젝트, PIE/패키징, 입력·카메라, prefab 생성, Nav/물리/저장 스모크 테스트 | 최신 main에서 요구 API 실제 사용, 최소 씬 실행 및 저장 복구 |
| M1 군체 프로토타입 | 작은 토템, 3~5개 동료, 추종/명령, 적층과 협동 운반 | 편성한 군체가 이동하며 탑을 만들고 무거운 물체를 옮길 수 있음 |
| M2 공명 및 전투 | 장승/솟대/모아이를 모티브로 한 원형, 자동/설치/군체 전투, 공명 | 동일 규칙으로 결계와 중계, 파손, 공명 단절, 물리 협동 가능 |
| M3 원정 | 허브와 수작업 탐험 맵 1개, 시간 위험도, 귀환/실패, 복원 지점, 개체 저장 | 정상 귀환/실패 후 모든 영구 상태가 정의대로 유지됨 |
| M4 제작·자동화 | 채집·창고·운반·가공·제작/수리, 배치 및 연결 UI | 원정 자원으로 토템을 수리·제작해 다음 출정에 활용하는 전체 루프 완성 |
| M5 확장 | 두 번째 지역, 시드 배치, 군체 성장, 최적화, 아트 개선 | 문화별 차이가 실제 플레이를 바꾸며 여러 원정 반복 가능 |

M0~M4에는 대규모 오픈월드, 완전 물리 군체, 복잡한 자율 경제, 전체 문화권 콘텐츠, 실제 포털 렌더링, GPU 물리, 멀티플레이를 포함하지 않는다. 필수 기능을 축소하여 실험하는 것이며 최종 기획에서 삭제한다는 뜻은 아니다.

### 16.1 초기 기술 검증 지표 (제안)

- 같은 경로로 10/30/100개 군체를 각각 이동시켜 평균 및 p95 프레임타임, 경로 처리량, 정체 및 도착률 기록.
- 초기 적층 2~4단을 평지/경사/급회전/충돌 환경에서 반복해 안정성과 해제 오류 검증.
- 운반 도중 파손, 대상 제거, 창고 포화, 도로 차단 및 작업 취소를 반복해 예약 누수/중복 인계 검사.
- 100 노드 공명망에 연결·해제·순환을 입력해 공급량 보존과 업데이트 시간 측정.
- 저장 후 불러오기, 원정 실패 및 중복 정산, 강제 종료 후 복구, 개체 ID 참조 검사.
- 초기 목표는 60fps(16.67ms 프레임 예산)로 제안하되 테스트 장비/백엔드/해상도와 달성 여부는 실제 계측 후 기록한다. 현재 수치는 성능 측정 결과가 아니다.

## 17. 후속 기획에서 정할 사항

- 세계관: 정령의 기원, 오염의 원인, 서사 및 문화권 연결의 구체적인 규칙.
- 군체: 초기·최대 규모, 원정 제한 방식, 개체별 성격·관계·성장 깊이.
- 편성: 비용/슬롯, 적층 제한, 원정 도중 재편성, 설치형 토템 회수 여부, 빙의의 필수 여부.
- 전투: 직접 공격 유무, 적 AI·보스, 전투와 탐험의 비중, 난이도 곡선.
- 원정: 지역 크기/시간, 귀환의 즉시성, 보존·계승 비율, 영입 직후 실패 시 처리.
- 자동화: 생산 깊이, 경로 직접 편집 방식, 원정 중/오프라인 생산, 방어 이벤트 발생 조건.
- 문화: 시작 지역, 실제 문화 모티브의 활용 범위, 자료 검증 및 자문.
- 아트: 로우폴리 팔레트·카메라 투영 방식, 화면 가독성, 음악과 연출 규칙.
- 기술: GPU/CPU 목표, 저장 버전, 프로젝트 구조, 물리·Nav 외부 라이브러리 선택, 배포 대상.
