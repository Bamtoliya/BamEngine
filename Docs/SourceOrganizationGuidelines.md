## 1. 목적과 적용 범위

같은 기능을 이해하거나 확장할 때 관련 데이터·처리·등록 경로를 예측할 수 있게 한다.
폴더 모양의 통일보다 책임·의존 방향·상태 소유권과 사용자의 학습 부담을 우선한다.
현재 Engine·Editor·Client의 구분과 독립 Projects 모듈을 출발점으로 점진적으로 적용한다.

새 코드와 수정하는 기능부터 적용한다. 규칙과 다르다는 이유만으로 저장소 전체를 한 번에 이동하지 않는다.
이 문서는 파일 수정·명령 실행·빌드·테스트의 허가가 아니며 루트 AGENTS.md의 작업 방식을 따른다.
이번 문서 작성 허가는 Markdown 범위이며 엔진 코드·빌드 설정 변경으로 확대하지 않는다.

## 2. 분류를 결정하는 순서

1. 실행에 필요한 기능인지, 제작용 처리인지, 호스트 또는 프로젝트 규칙인지 구분한다.
2. 어떤 코드가 어떤 기능을 알아야 하는지 의존 방향을 정한다.
3. 해당 데이터·알고리즘·상태를 소유하는 기능을 정한다.
4. 공유 에셋·실행 인스턴스·GPU·편집 상태의 수명과 변경 책임을 구분한다.
5. 그 안에서 공개 계약과 내부 구현을 Public·Private로 배치한다.

클래스 이름에 Component·System·Manager·Resource가 붙었다는 이유만으로 최상위 위치를 결정하지 않는다.
역할이 다른 코드는 구분하되 같은 기능의 변경으로 함께 수정되는 코드를 가까이 둔다.
여러 기능이 사용한다는 사실만으로 Core에 올리지 않고, 특정 기능의 의미 없이도 사용할 수 있는지 확인한다.

## 3. 실행·제작·호스트·외부 연동의 경계

- Engine: PIE·Client·학습 실행이 공유하는 데이터 해석, 시뮬레이션과 렌더링 기능을 소유한다.
- Editor: 편집 문서·선택·명령 이력·패널·제작 작업 흐름을 소유하고 Engine의 실행 기능을 호출한다.
- Tools 또는 UI 없는 제작 처리: 임포트·변환·코드 생성·Cook·Stage·Package를 담당한다.
  재사용 요구가 확인되면 Editor UI와 처리 코드를 분리하며 처음부터 별도 실행 파일을 강제하지 않는다.
- Client 등 호스트: 창·입력 수집 경계·실행 루프·실행 구성·프로젝트 시작을 담당한다.
- 프로젝트 모듈: 게임 규칙·과제별 보상식·프로젝트 고유 아바타 동작을 소유한다.
- 외부 연동: Python·학습 프레임워크·추적 SDK·방송 출력은 공통 실행 계약을 사용하는 어댑터로 연결한다.

플랫폼 구현은 먼저 해당 기능의 Platform 하위에 둔다. RHI의 DirectX12·SDLGPU 경계가 그 예다.
실제로 여러 기능이 공유하는 플랫폼 기능만 공통 기반으로 추출한다.
제작 데이터와 변환된 실행 데이터를 구분하고, Client가 Editor 개인 설정·패널·원본 제작 환경에 의존하게 하지 않는다.

## 4. 엔진 공통 책임과 기능 소유자

### Core

기본 타입·기하 및 수학 연산·이벤트·기반 인터페이스처럼 특정 게임 기능을 몰라도 되는 코드를 둔다.
정점 입력 레이아웃·셰이더 바인딩·GPU 상수 자료형을 단순 구조체라는 이유로 Core/Structs에 모으지 않는다.
공통 기하 값과 Collider의 편집 설정은 좌표계·유효성·소비자가 같을 때만 재사용한다.

현재 Core의 엔진 ReflectionRegistry는 구체 컴포넌트와 코덱을 연결하는 엔진 통합 코드다.
독립 Projects/Reflection과 같은 계층으로 간주하지 않는다. 경로 통일이 의존 방향의 해결을 의미하지 않으며,
기능별 등록 내용과 시작 시 조합 책임은 필요한 범위에서 점진적으로 정리한다.

### World

Entity·Scene·계층·공통 컴포넌트 접근과 ECS 시스템 실행 기반을 둔다.
이름·ID·계층·Transform 같은 공통 장면 데이터의 소유 후보이며, 물리·오디오 등 구체 기능의 저장소로 만들지 않는다.
공통 시스템 인터페이스와 스케줄러는 가까이 두고, 개별 PhysicsSystem·AudioSystem은 해당 기능이 소유한다.
SystemManager의 위치 통일과 World 아래로의 책임 정리는 별도 단계로 진행할 수 있다.

### Resource

공통 핸들·참조 관리·로딩·캐시·등록 계약을 담당한다.
구체 리소스는 저장된다는 이유보다 기능 소유자를 먼저 검토한다.
기존 Resource/Model·Material 등의 일괄 이동은 요구하지 않으며 해당 기능을 확장할 때 데이터와 실행 책임을 함께 확인한다.
저장 형식·확장자·리소스 타입 판정이 여러 UI나 내부 함수에 복제되지 않도록 공통 계약을 재사용한다.

### Runtime

사용할 기능과 실행 구성을 조합하고 초기화·실행 단계·종료 순서를 연결한다.
물리 해결기·애니메이션 평가·임포트 알고리즘을 Runtime에 넣지 않는다.
폴더 재배치와 싱글턴 전면 교체를 같은 작업으로 묶지 않는다.
창·렌더러·오디오 없는 수치 실행과 화면 없는 GPU 센서 실행은 별도 구성으로 검증한다.

### 기능 영역

Render·Physics·UI·Graph·Audio·Input·Time·Terrain 등은 자신의 데이터·처리·상태와 연결 API를 소유한다.
Animation·파티클·스플라인 등 새 영역은 실제 구현을 시작할 때 필요한 파일만 만든다.
Manager·Utility·Common 같은 이름만으로 책임을 설명하는 최상위 수납 공간을 늘리지 않는다.

## 5. 폴더와 파일의 기본 형식

기본 형식은 `기능/Public`, `기능/Private`다. 하위 기능이 분명하면 `Render/Shader/Public`처럼 확장한다.
기능 이름과 Public·Private의 계층 순서를 같은 영역에서 혼용하지 않는다.
헤더와 구현의 하위 책임 구분을 대응시키고, 파일이 적으면 Components·Queries 같은 하위 폴더를 억지로 만들지 않는다.

다음은 목표 형식의 예시이며 현재 경로 또는 구현 완료 목록이 아니다.

```text
Physics/
  Public/
    Collision.h
    PhysicsSystem.h
    Components/
      ColliderComponent.h
      RigidBodyComponent.h
  Private/
    Collision.cpp
    PhysicsSystem.cpp
```

Core의 Reflection·Module을 먼저 같은 형식으로 정리할 수 있다.
Components 전체 이동은 각 기능의 소유 위치·참조 경로를 확정한 뒤 기능별로 진행한다.
Public은 소비자에게 필요한 계약이며, Public 폴더에 있다는 이유로 내부 캐시·작업 큐·변경 가능한 상태를 공개하지 않는다.

## 6. 상태와 자원의 구분

- 공유 에셋: 클립 키·골격 정의·그래프·효과 설정. 여러 인스턴스가 같은 정의를 사용할 수 있다.
- 실행 상태: 재생 시간·현재 포즈·그래프 변수·물리 접촉·난수·이벤트 큐. Scene·엔티티·실행 세션 수명에 연결한다.
- GPU 상태: 버퍼·텍스처·디스크립터·프레임별 제출과 업로드 상태. 소유자와 GPU 완료 후 해제를 명시한다.
- 편집 상태: 선택·미저장 변경·Undo 이력·편집 초안·패널 배치. 실행 데이터와 구분한다.

폴더가 같아도 객체·컨테이너·저장 대상은 구분한다. 구분을 위해 항상 별도 클래스가 필요한 것은 아니다.
같은 클립의 두 캐릭터, Editor 미리보기와 PIE, 독립 학습 환경이 변경 가능한 상태를 공유하지 않게 한다.
씬 Archive 복원만으로 타이머·물리·스크립트·GPU·외부 통신의 초기화가 끝났다고 가정하지 않는다.

## 7. 의존 방향과 확장 접점

- 공통 계약은 실제 소비자들이 의존할 수 있는 위치에 둔다. 하위 계층이 상위 기능의 자료형을 가져오지 않게 한다.
- 연결 코드는 양쪽 기능을 알 수 있지만, 독립 기반 모듈에 엔진 전용 의미를 역으로 넣지 않는다.
- Projects/Reflection·Archive·ReflectionArchive는 엔진 Base·싱글턴·경로·초기화 순서를 요구하지 않는다.
- 리소스·컴포넌트·그래프·스크립트의 등록은 기존 코드 생성과 레지스트리를 활용한다.
  새 기능 때문에 중앙 파일과 여러 수동 타입 목록을 반복 수정하는 부담을 줄이되 새로운 중복 등록 체계를 만들지 않는다.
- 기능별 등록과 실행 순서의 조합은 구분한다. 등록 순서가 자원 생성·해제 순서를 대신하지 않는다.

현재 RegisterExplicitLoader와 RegisterComponentOperations의 중앙 결합은 폴더 이동만으로 해결되지 않는다.
새 타입을 추가하는 작은 사용 흐름에서 수정 범위를 확인하고 필요한 공개 등록 경계부터 보완한다.
엔진 API·저장 형식·플러그인 ABI 변경은 단순 파일 이동과 별도로 검토한다.

## 8. PCH와 include의 기준

엔진의 통제된 빌드에서는 STL·C 표준 헤더를 Engine_Includes.h의 공통 영역에서 공급하는 방침을 사용한다.
사용하는 모든 표준 헤더를 개별 엔진 파일에 다시 직접 포함하는 규칙은 적용하지 않는다.
반드시 포함되는 기반 헤더가 이미 제공하는 정의도 활용할 수 있다.

정리 절차는 다음과 같다.

1. PCH 직접 포함, 엔진 헤더를 통한 포함, 서드파티 내부의 간접 포함과 미등록 사용을 구분한다.
2. 중앙화할 표준 헤더를 엔진 자체 헤더보다 먼저 공급하고 기존 파일의 반복 include를 제거한다.
3. Types·Logger·Delegate처럼 현재 공급원인 헤더에서 제거할 때는 PCH 공급 순서를 먼저 맞춘다.
4. Engine·Editor·Client·검사 타깃과 리플렉션 파서의 공통 진입 경로를 확인한다.
   PCH가 PRIVATE라는 이유로 각 파일에 표준 include를 다시 늘리기보다 타깃 또는 공통 진입부의 계약을 정한다.
5. 독립 Projects 모듈은 자신의 공통 헤더·빌드 계약을 사용한다. Engine PCH를 독립 모듈의 필수 의존성으로 만들지 않는다.

Debug의 new 매크로·CRT 설정과 서드파티 구현 매크로가 필요한 include는 별도로 검토한다.
STB_IMAGE_IMPLEMENTATION 같은 구현 생성 헤더를 표준 헤더와 함께 PCH로 이동하지 않는다.
묶음 헤더는 제공할 기능 집합을 설명하는 역할도 있으므로 단순 줄 수 감소만으로 해체하지 않는다.
반복 include 제거가 곧 헤더 파싱 비용이나 빌드 시간의 같은 비율 감소를 뜻하지 않는다.

## 9. 헤더·구현의 읽기 순서

파일의 역할에 맞춰 관련 타입·생성/종료·공개 기능·내부 처리·멤버 상태의 흐름을 정한다.
기능별 영역과 그 안의 함수 순서를 헤더와 구현에서 대응시킨다.
여러 구현 파일로 책임 있게 나눈 SceneArchive·SceneHierarchy 등을 순서 통일 때문에 합치지 않는다.
MyRegion 같은 임시 영역명과 의미 없는 반복 구분을 정리하고 실제 책임을 이름에 드러낸다.

멤버는 스트림·인덱스·경계·캐시처럼 관련 상태를 모으고 타입 정의·함수 선언과 섞지 않는다.
멤버 이동은 초기화 순서·객체 배치·반사 정보·저장 형식·GPU 전달 배치에 미치는 영향을 확인한 뒤 진행한다.
함수 선언 순서 정리와 이진 헤더·상수 버퍼 필드 재배치를 같은 가독성 수정으로 취급하지 않는다.

## 10. 현재 코드의 이관 후보와 적용 경계

아래는 2026-10-24 정적 조사에 근거한 후보이며 파일 이동이 완료됐다는 뜻이 아니다.

- Core/Reflection·Module: 기능/Public·Private 순서 통일. ReflectionRegistry의 엔진 통합 책임은 별도로 표시한다.
- Core/Structs/Vertex와 Core/Private/Vertex: Render의 정점·입력 레이아웃 소유 위치와 헤더/구현 경로를 맞춘다.
  SceneUBO는 오브젝트 전달 데이터로 구분하고 바인딩·필드 배치를 보존한다.
- Resource/Shader의 공통 타입·반사 처리: RHI와 리소스가 사용할 Render 공통 계약을 검토한다.
  ReflectSPIRV의 SDLGPU 사용을 보존하며 반사 전체를 Editor로 옮기지 않는다.
- System의 서비스와 ECS 처리: Input·Time·Audio 서비스는 기능이 소유하고 공통 스케줄러만 공통 실행 기반에 둔다.
- System/Terrain의 TerrainUtility: 공용 지형 계산·브러시·이미지 입출력과 ECS 갱신의 책임을 구분한다.
  분류 정리를 이유로 필요한 처리까지 Editor 전용으로 만들지 않는다.
- Utility/Picking: 렌더 피킹 ID·패스·프레임 관리의 소유 후보는 Render/Picking이다.
  Collider 기반 게임 질의는 Physics 또는 World 연결 경계에서 별도로 제공한다.
- Interface의 Delegate와 EventBus: 이벤트 기능의 관계를 반영한다. Handle·Result·EnumBit은 실제 역할로 분류한다.
- PhysicsManager·TimerManager 등 선언만 남은 후보: 호출·생성·외부 사용과 유지 의도를 확인한 뒤 이관·정리한다.

파일이 여러 영역에 있다는 사실만으로 결함으로 판단하지 않는다.
현재 Resource/Model의 에셋 데이터와 Scene의 책임별 구현 파일은 관련 기능을 실제로 확장할 때 재평가한다.

## 11. 이관 절차와 검증

1. 해당 기능의 현재 경로·참조·소유자·생성/종료 순서를 기록한다.
2. 새 경로와 공개 계약, 남길 호환 경계와 변경할 문서를 정한다.
3. 한 기능 또는 작은 파일 쌍씩 이동한다. 이동·이름 변경·동작 변경·직렬화 변경을 분리한다.
4. CMake의 include 수집·하드코딩 경로·리플렉션 생성 입력·검사 타깃·도구 스크립트·문서 링크를 확인한다.
5. 생성 파일을 수동으로 고치지 않고 원본·생성 설정을 정리한다. 호환 전달 헤더를 남기면 용도와 제거 조건을 기록한다.
6. 사용자에게 영향 타깃의 빌드·관련 검사·PIE 반복·씬 저장/복원·리사이즈·자원 해제 확인 방법을 제공한다.
7. 정적 확인과 사용자가 수행한 실행 결과, 미검증 소비자·플랫폼을 구분해 기록한다.

파일 이동만으로 컴파일 시간·헤드리스·플러그인·다중 환경 지원이 개선됐다고 주장하지 않는다.
기존 사용자 변경과 공개 API·타입 식별자·로캘 키·저장 키·바인딩 ABI를 보존한다.
전체 재배치 완료를 모든 기능 개발의 선행 조건으로 두지 않는다.

## 12. 문서와 계획의 관계

분류·PCH·파일 조직 기준은 이 문서에서, 문서 간 우선순위와 보류 조건은 DevelopmentPriorities에서 관리한다.
각 개발 계획은 기능 계약·선행 조건·완료 예제를 유지하고 통합 순서를 중복해서 새로 정의하지 않는다.
장기 계획의 이름과 폴더가 존재한다는 사실을 구현·실행·성능 검증의 근거로 사용하지 않는다.
