# 텍스처·스프라이트 편집기 통합 계획

- 작성일: 2026-11-20
- 상태: **설계 제안. 통합 구현 및 실환경 검증 전.**
- 범위: 텍스처 정보·변환과 스프라이트 저작의 에디터 작업 흐름. 씬 엔티티용 `InspectorPanel`은 제외한다.

## 1. 목적과 현재 상태

같은 이미지를 확인하고 변환한 뒤 스프라이트로 편집할 때 여러 창과 진입점을 오가는 불편을 줄인다. 목표는 **작업창의 통합**이며, 텍스처와 스프라이트를 같은 리소스나 같은 저장 문서로 합치는 것은 아니다.

| 구성 | 현재 확인한 역할 |
|---|---|
| `TextureEditor` | 이미지 및 `.bamtex` 등의 썸네일과 기본 정보를 표시한다. |
| `SpriteEditor` | 텍스처 또는 스프라이트를 열어 슬라이스·피벗·보더를 편집하고 별도 스프라이트 파일을 저장한다. 문서 이력과 애니메이션 생성 기능이 있다. |
| `TextureInspector` | 텍스처 변환 설정과 자동 스프라이트 생성 UI가 있으나 생성·등록·호출 경로가 확인되지 않았다. 현재 접근 가능한 UI라고 가정하지 않는다. |

`ImGuiManager::FindResourceEditor()`는 처음 지원하는 편집기를 선택한다. 텍스처와 스프라이트의 지원 확장자가 겹치는 경우 현재 등록 순서상 일반 열기는 텍스처 편집기를 선택한다. 콘텐츠 브라우저의 우클릭 메뉴에는 스프라이트 편집기를 직접 여는 별도 경로가 있다.

`TextureEditor`는 `AssetCache`의 썸네일을 사용하고 `SpriteEditor`는 텍스처 리소스 핸들을 사용한다. 두 경로를 같은 자원 또는 동일한 해상도의 미리보기라고 가정하지 않는다.

## 2. 제안하는 구조

하나의 리소스 편집 창에 **정보·변환**과 **스프라이트 편집**을 탭 또는 모드로 제공한다. 화면 배치와 구체적인 클래스 분리는 구현 설계 시 기존 코드와 비교해 결정한다. 하나의 창이라고 해서 모든 기능과 상태를 하나의 거대한 클래스에 모을 필요는 없다.

- 이미지 또는 `.bamtex`를 일반적으로 열면 정보 화면을 표시하고, `.bamsprite`를 열면 스프라이트 편집 화면으로 진입한다. 기존 스프라이트 우클릭 메뉴도 스프라이트 모드로 연결한다.
- 정보·변환은 대상 텍스처의 경로와 미리보기를 표시하고, **지원하는 원본**에서 출력 형식과 압축 방식을 선택해 변환한다. 변환 가능한 입력은 실제 변환기의 지원 범위를 기준으로 표시한다.
- 스프라이트 화면은 기존 캔버스, 슬라이싱, 속성, 저장, 이력 및 애니메이션 생성 기능을 유지한다. 스프라이트를 열었을 때 참조 텍스처를 확인할 수 없는 경우에는 오류를 알리고 없는 원본 경로를 추정하지 않는다.
- `TextureInspector`의 유용한 변환 기능은 지원 여부와 수명·오류 처리를 확인해 이관한다. 기존 코드를 그대로 호출하지 않으며, 이관과 참조 확인이 끝나기 전에는 클래스를 삭제하지 않는다.

기존 두 창을 유지하고 서로 여는 버튼만 추가하면 변경이 작고 문서 수명도 분리되지만, 화면 전환은 남는다. 반면 단일 클래스로 모두 합치면 책임이 섞인다. **하나의 작업창과 분리된 작업별 책임**을 추천한다.

## 3. 상태·저장 및 변환 안전성

- 텍스처 변환은 산출물 생성 작업이고, 슬라이스 저장은 텍스처를 참조하는 별도 스프라이트 문서를 저장하는 작업이다. 저장·변환 버튼과 결과의 대상을 명확히 표시한다. 스프라이트 Undo/Redo와 미저장 상태를 변환 설정 변경과 혼동하지 않는다.
- 탭 또는 모드 전환만으로 미저장 슬라이스와 이력을 잃지 않는다. 다른 대상 열기·드롭·닫기·종료는 기존 `ResourceEditorInterface`의 문서 교체·닫기 보호를 따르며, 저장 실패나 취소 시 편집 상태를 유지한다.
- 변환 중에는 중복 요청을 막고, 대상 전환이나 창 닫기 후 완료된 작업이 다른 대상에 결과를 적용하지 않도록 요청 대상과 수명을 관리한다. 변환 산출물과 열린 스프라이트가 충돌하거나 갱신이 필요한 경우를 확인하고, 미저장 편집을 조용히 덮어쓰지 않는다.
- 기존 출력 덮어쓰기 확인, 실패 시 기존 파일 보존, 취소 및 오류 알림을 처리한다. `Engine://` 읽기 전용 정책을 준수하며 쓰기 가능 여부를 대상과 출력 경로 모두에서 확인한다.
- 변환 결과가 표시·사용되는 경로에서 썸네일 및 리소스 캐시의 갱신 필요성을 확인한다. 갱신이나 핸들 교체가 진행 중 편집에 미치는 영향을 함께 검증한다.
- 기존 CPU 표준·CPU 빠른 BC7·GPU BC7 선택을 연결한다. GPU 경로와 지원 형식의 실제 제한 및 CPU 폴백을 표시 또는 로그로 구분한다. 미지원 플래그를 동작하는 옵션처럼 노출하지 않는다.
- 원본 파일과 생성된 `.bamtex`의 역방향 연결이나 저장된 임포트 옵션 복원은 현재 보장되지 않는다. 새 원본 추적·설정 영속화는 [에셋 임포트 설정 계획](ImGuiDevelopmentPlan.md)에서 별도 범위로 다룬다.

## 4. 진행 순서

1. **진입점과 문서 경계 확인**: 이미지·`.bamtex`·`.bamsprite` 열기, 우클릭, 드롭, 창 메뉴, 단축키 및 작업공간 복원 경로와 기존 저장 보호를 확인한다. 기존 진입점과 사용자 설정의 호환 정책을 정한다.
2. **통합 작업창 구성**: 기존 스프라이트 기능을 보존하면서 대상별 진입과 모드 전환을 연결한다. 슬라이스 문서·이력은 모드 변경 중 유지하고 실제 문서 교체 시 기존 확인 경로를 사용한다.
3. **텍스처 변환 연결**: 미연결 인스펙터의 지원 가능한 기능을 통합 창에 이관한다. 출력 충돌·읽기 전용·비동기 수명·성공/실패·캐시 반영을 함께 처리한다.
4. **정리와 문서화**: 기존 패널 등록, 직접 참조, 단축키 문맥, 창 이름과 작업공간 설정 및 로캘 키를 점검한다. 호환성과 기능 이관을 확인한 뒤에만 중복 코드를 정리한다. 현행 문서와 구현 기록에 실제 결과와 미검증 항목을 반영한다.

표시 문구는 기존 키를 우선 사용하고 필요한 변경은 에디터 로캘 CSV 원본에 반영한다. 단축키는 `EditorActionRegistry`/`ShortcutManager`, 속성 행과 모달은 공통 UI 지침을 따른다.

## 5. 완료 및 검증 기준

- 이미지, `.bamtex`, `.bamsprite`와 기존 우클릭·드롭 진입이 의도한 화면을 연다. 기존 파일 열기·스프라이트 슬라이싱·저장·애니메이션 생성이 유지된다.
- 슬라이스 편집 후 모드 전환, 다른 파일 열기·닫기·종료의 저장/버리기/취소, 저장 실패와 Undo/Redo를 확인한다. 텍스처 변환이 슬라이스의 미저장 상태를 해제하지 않는다.
- CPU 표준·빠른 BC7·GPU BC7에서 실제 사용 backend와 GPU 실패 시 CPU 폴백을 구분한다. 캐시 적중과 최초 압축은 별도로 측정한다. 변환 중 전환·닫기, 출력 충돌, 실패·취소, 캐시 갱신과 `Engine://` 보호를 확인한다.
- [에디터 UX 검증 기준](EditorUXTestGuidelines.md)에 따라 정적·헤드리스 자동 검사와 실제 에디터 검증을 구분한다. 한·영 전환, 좁은 도킹 폭, UI 배율 및 단축키 문맥도 확인한다.
- 기존 워커·스프라이트·로캘 관련 검사와 변경 범위에 맞는 회귀 검사를 사용자가 실행한다. 기존 워커 테스트 통과만으로 통합 UI, 실제 GPU 사용 또는 속도·화질이 검증됐다고 판단하지 않는다.
