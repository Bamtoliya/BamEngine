# 리플렉션·아카이브 개발 목표와 작업 지침

## 1. 이 문서의 목적

Reflection, Archive, ReflectionArchive, ReflectionEnTT 관련 작업에서
처음 정한 목표를 잊지 않고 구현과 설계의 판단 기준으로 사용한다.

이 문서는 목표와 제약을 기록한다.
현재 코드에 기능이 존재하거나 동작이 검증되었다는 뜻은 아니다.
작업 방식은 루트 AGENTS.md를 따른다.

## 2. 최종 목표

사용자가 구조체·클래스와 저장 대상 멤버를 리플렉션에 등록하면,
타입마다 별도의 저장·불러오기 함수를 작성하지 않아도
공통 API를 통해 편하게 저장하고 복원할 수 있도록 한다.

이 기능은 BamEngine에 종속되지 않아야 하며,
다른 프로젝트에서도 재사용할 수 있어야 한다.

설계와 구현을 평가할 때 다음 질문을 우선한다.

- 새 타입을 등록한 뒤 저장·복원하려면 사용자가 무엇을 추가로 작성해야 하는가?
- 같은 멤버 정보를 리플렉션 등록과 직렬화 코드에 중복 작성하고 있지 않은가?
- 다른 프로젝트에서 사용하려면 엔진 전용 코드까지 가져와야 하는가?

## 3. 사용자가 작성할 코드와 시스템이 처리할 코드

사용자는 타입과 멤버를 선언하고 리플렉션 대상으로 등록한다.
저장·복원은 공통 API를 호출하여 수행한다.

일반적인 등록 타입마다 다음 코드를 반복 작성하게 하지 않는다.

- 멤버를 하나씩 나열하는 저장 함수
- 같은 멤버를 다시 나열하는 복원 함수
- 저장 형식마다 별도로 작성하는 타입별 변환 함수

등록된 멤버를 순회하고 적절한 저장·복원 처리를 선택하는 일은
리플렉션과 직렬화 연결 계층이 담당한다.

내부 구현에 어댑터나 코덱이 필요할 수 있다.
그러나 구현 편의를 위해 일반적인 타입의 처리 책임을 사용자에게 넘기지 않는다.

리소스 참조처럼 별도의 의미 해석이 필요한 타입은 확장 지점을 제공한다.
이때 예외 처리가 필요한 이유와 사용자에게 요구하는 추가 작업을 명시한다.

## 4. 모듈의 책임과 재사용성

### Reflection

- 타입·멤버·함수·enum과 메타데이터를 등록하고 조회한다.
- 등록된 객체의 멤버에 접근하는 기능을 제공한다.
- 엔진과 저장 형식의 세부 정책에 의존하지 않는다.

### Archive

- 값·객체·컨테이너의 저장과 복원에 필요한 공통 API를 제공한다.
- JSON·BEVE 등 저장 형식과 문서·파일 입출력을 처리한다.
- Reflection과 엔진 없이도 사용할 수 있어야 한다.

### ReflectionArchive

- Reflection에 등록된 정보를 Archive의 저장·복원 처리로 연결한다.
- 등록 타입마다 수동 직렬화 함수를 작성할 필요를 줄이는 핵심 계층이다.
- 타입별 확장과 직렬화 정책을 처리하되 엔진 전용 기능을 포함하지 않는다.

### 소비 프로젝트

- 사용할 타입을 등록하고 공통 저장·복원 API를 호출한다.
- 리소스 조회와 엔티티 관계 복원 등 프로젝트 고유의 의미를 처리한다.
- 프로젝트 전용 타입의 확장을 위해 공통 모듈을 직접 수정하지 않도록 한다.

독립 모듈은 엔진의 기반 클래스, 싱글턴, 경로 구조와 초기화 순서를 강제하지 않는다.
재사용성은 폴더 분리뿐 아니라 별도 소비 프로젝트의 사용 흐름으로 확인한다.

## 5. 자동 저장·복원의 정확성

편리한 API를 제공하더라도 데이터가 정확히 복원되어야 한다.

- 등록된 대상과 실제 객체 타입이 일치하는지 확인한다.
- 값 복사와 원본 참조를 구분하여 올바른 객체를 수정한다.
- const와 실제 쓰기 가능 조건을 지킨다.
- 지원하지 않는 타입을 조용히 생략하거나 성공으로 처리하지 않는다.
- 필드 누락, 잘못된 값과 타입 불일치를 구분하여 오류를 전달한다.
- 저장 제외와 선택적 필드의 정책을 명확히 한다.
- 실패 시 대상 객체와 기존 파일이 보존되는 범위를 구분하여 설명한다.

포인터 대상, 객체 관계와 리소스의 자동 복원은
일반 멤버 값의 복원과 같은 문제로 취급하지 않는다.
해당 기능이 필요하면 소유권과 참조 해결 정책부터 정한다.

## 6. ReflectionEnTT의 목적

ReflectionEnTT는 기존 Reflection을 대체하기로 결정한 구현이 아니다.

Reflection, Archive, ReflectionArchive를 완성한 뒤
성능을 비교하기 위해 준비한 별도 구현이다.

따라서 다음 원칙을 따른다.

- 현재 작업의 우선순위는 기존 시스템의 목표 달성과 정확성 확보다.
- 성능 비교를 이유로 기존 시스템의 완성을 미루지 않는다.
- EnTT의 구조를 기존 시스템이 반드시 따라야 할 정답으로 취급하지 않는다.
- 비교 결과를 얻기 전에 어느 쪽이 더 빠르다고 단정하지 않는다.
- 대체나 통합은 비교 결과와 변경 비용을 확인한 뒤 별도로 판단한다.

비교할 때는 같은 데이터와 동등한 기능·검사 조건을 사용한다.
코드 생성 시간, 등록 시간, 런타임 접근과 저장·복원 시간을 구분한다.
저장 형식과 파일 입출력 비용이 결과에 포함되는지도 명시한다.

## 7. 변경과 완료의 판단 기준

변경을 제안할 때는 다음을 설명한다.

1. 최종 목표의 어떤 부분을 해결하는가?
2. 사용자가 반복 작성해야 하는 코드가 줄어드는가?
3. 책임과 의존 방향이 유지되는가?
4. 현재 구조에서 작은 변경으로 해결할 수 있는가?
5. 정상 동작과 실패 처리를 어떻게 확인할 것인가?

완료 여부는 다음 사용 흐름으로 판단한다.

- 일반적인 구조체·클래스와 멤버를 등록한다.
- 타입별 수동 직렬화 함수 없이 공통 API로 저장한다.
- 공통 API로 복원하여 저장 대상 값이 일치하는지 확인한다.
- 잘못된 입력에서 오류와 대상 상태를 확인한다.
- 엔진 밖의 소비 프로젝트에서도 같은 흐름을 확인한다.

기능 구현, 정적 검토와 실행 검증을 구분하여 기록한다.
일부 타입의 성공을 모든 등록 타입의 지원으로 일반화하지 않는다.
